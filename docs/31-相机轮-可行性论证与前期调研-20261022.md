## 0. 结论摘要

**可行性=中高，比 22 号的 P3 估计乐观**。理由：sdm845 的 CAMSS 支持在 mainline 是**活跃开发中的既成事实**（非"待移植"），有 **OnePlus 6/6T IMX519 主摄实测先例**（C-PHY 刚突破 2026-01），且 **gitlab.com/sdm845-mainline 社区有 6.18.2 完整分支**（离我们的 6.19.14 仅两个版本）。**硬限制：仅 RDI（raw dump），无 ISP 后处理**（Titan 170 的 BPS/IPE 因高通法律原因未进 mainline）。

## 1. 分项把握度（评估格式：分项/百分比/依据）

| 分项 | 把握度 | 依据 |
|---|---|---|
| CAMSS 框架在我们的 6.19 内核编译通过 | **90%** | 树内已有 camss 全套源码（csid-gen2/csiphy-3ph/vfe170 等 Titan170 组件文件都在），Kconfig 依赖 IOMMU_DMA/V4L_PLATFORM 满足；剩 10%=编译告警级问题 |
| camss + sdm845 DT 在本机 probe 通（不挂死） | **75%** | sdm845-mainline 分支有完整 dts+config（6.18.2 tag 刚确认）；ixit 团队给 845 加了命名电源域支持；剩 25%=本机 PMIC/电源域差异（29 号差异清单适用） |
| 前/主摄 sensor 探测成功（拿到 chip ID） | **60%** | 依赖两个未知：①本机 sensor 型号（vendor DT 不含型号字符串，需设备在线时从 vendor 分区/运行时提取）②主线是否有该型号驱动（i2c 下 imx/gc/hi/ov 系驱动齐全，若型号是主流款则高、若是定制款则需改 CCS 适配） |
| RDI 模式采集 raw 帧成功 | **55%** | OnePlus 6/IMX519 是先例（C-PHY）；本机若用 D-PHY sensor 更简单（D-PHY 路径成熟）；风险=C-PHY/D-PHY 需本机确认 + lanes 配置要从 vendor DT 移植 |
| 变成"能拍照"（v4l2→用户态存图） | **70%** | 一旦 RDI 通，v4l2-ctl/libcamera 可直采 raw；用户态工作量小；但**画质=传感器原始输出**（无降噪/HDR/去马赛克在 ISP，需用户态 dcraw 类处理） |
| 双摄/结构光组件（depth/ir/iris/fisheye） | **10%** | vendor DT 有节点但①硬件是否实装未知（可能是家族通用 DT）②结构光=专有算法，主线零支持 |

## 3. 本机相机硬件清单（vendor-full.dts，equuleus 真身）

- **sensor 槽位**：`rear` + `rear2`（双主摄）+ `front` + `depth`/`ir`/`iris`/`fisheye`（结构光组件——**DT 有节点≠硬件实装**，待实测）
- **IP 块**：csiphy×12 lane 配置、csid×2（csid170）、vfe0+vfe1（vfe170 双 VFE）、cci、jpegenc/jpegdma、cpas——**标准 Titan 170 布局**
- **actuator×5、eeprom**（对焦马达/标定数据）
- **sensor 型号：DT 无字符串**（qcom 平台型号在 eeprom blob/bootloader 注入）——**需设备在线时从 vendor 分区提取**（下一次联调的前置任务）

## 4. 路径设计（用户回来后的执行序）

1. **前置**：从设备 dd vendor 分区（几百 MB，一次性）→ 提取 sensor 型号/标定 blob/原厂 camera DT 参数
2. **基线选择**：以 sdm845-6.18.2-r0 的 camss+dts+config 为基线 cherry-pick 到我们 6.19 树（版本距离小）
3. **config**：启用 VIDEO_QCOM_CAMSS + 对应 sensor i2c 驱动 + media/v4l2 栈（用社区 sdm845.config 对照）
4. **DT**（受 29 号铁律约束——appended dtb 无效！）：sensor 接线+csiphy lanes 需进 **fdtoverlay= 或 FV blob**——**这是相机轮的结构性障碍**：camera DT 必须在真 DT 里生效——**先做 fdtoverlay 路线验证（屏幕轮同需求）**
5. **验证链**：camss probe 不挂 → CCI 探测 → sensor chip ID（RDID 式读）→ RDI 流采集 → v4l2-ctl 抓帧
6. **判据**：`media-ctl -p` 显示完整管线；`v4l2-ctl --stream-mmap` 出 raw 帧且尺寸/帧率正确

## 5. 完全未知（诚实清单）

1. **本机 sensor 具体型号**（大概率=米8 原厂配置，但屏幕/触摸/指纹都换过第三方——相机换没换过无记录）
2. **相机硬件是否实装完整**（结构光组件在屏下指纹版上可能被砍——DT 是家族通用）
3. **fdtoverlay= 路线在 edk2+EFI stub 组合下的实际可用性**（理论支持，本机从未实测——**屏幕轮也依赖它**）
4. **C-PHY/D-PHY 选择**（米8 主摄大概率 C-PHY（IMX 系高像素），未确认——影响 lanes 配置路线）
5. **vendor 分区的提取条件**（fastboot 无 read 命令——需系统起来后 dd——等设备回 Debian）

## 7. 补充：原厂 ISP 移植评估修正（2026-10-22 深夜，techpack 源码实证）

用户提出"ISP 可以从原厂移植"后下载实证（`scratch/techpack-camera`，msm-4.19 camera-kernel 镜像）：

1. **许可翻案**：采样头为 **`SPDX-License-Identifier: GPL-2.0-only`**（Linux Foundation/Qualcomm copyright）——**不是 Apache，许可与内核兼容** ✓。Robert Foss 2021 说的 legal considerations 应指**固件 blob**（IPE/BPS 微码=专有，只能留用户空间/提取加载）或其他文件——**驱动代码移植的许可障碍从 ★★★ 降为 ★**。
2. **规模实锤**（.c 行数）：cam_isp **54,682** + cam_req_mgr 7,517 + cam_icp 10,315（IPE/BPS 固件管理器）+ cam_smmu 4,046 + cam_cpas 4,555 ≈ **8 万行核心**（+cam_sensor_module/cam_cdm 全家超 10 万）——**工作量障碍仍 ★★★ 决定性**：这栈为 vendor 内核 API 写（ION/dma-buf 私有路径、msm 内核内部接口），移植=大量改写+与 mainline camss 对接重写 VFE PIX。
3. **结论微调**：原厂 ISP 从"三障碍"变"两障碍"（许可过关、固件可提取、**工作量仍是月级**）——**短期最优路线不变**（RDI+libcamera 用户态 ISP，社区既定路线）；**长期保留为选项**（若 RDI 画质不满意，GPL 许可使得移植在法律上干净可行，可评估渐进式移植 cam_icp 子集）。techpack 源码已存档作第一手参考。
