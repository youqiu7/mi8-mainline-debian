## 2. 挂死分析（**最终真相，2026-10-22 23:00——推翻全部先前版本**）

**真凶：initramfs 残缺。** 从 V1 EFI 提取内嵌 initramfs（gzip cpio @ Image 偏移 0x23ff1ac）与 v1-v6 对比：
- V1（活）：`dev init lib newroot proc sys tmp`——完整启动系统（/init + switch_root）
- **v1-v6（我重编的所有版本）：只有 `ath10k qcom`——纯固件目录，没有 /init** → 内核 probe 打完 panel 日志后 panic: no working init。

**根源**：重编时 config 的 `CONFIG_INITRAMFS_SOURCE` 指向 `/root/initramfs-fw/root`——那是当年为 ath10k 补固件做的残缺目录，被误当作完整 initramfs。**编译器（gcc14/clang19）、驱动宽容化（RDID/exit sleep 后继续）、SMBB config 全部无罪**——tolerant v1/v2/v3/v4/v5/v6 的"挂死"全是同一原因，相关推断（27号§2 各版本、29号§3 v4 解读）作废。

**v7 修复**：INITRAMFS_SOURCE 改为 V1 解包出的完整 initramfs（/root/initramfs-full），1930 原版驱动+clang19 重编——预期恢复 V1 行为基线；随后可安全重跑宽容化实验拿 -22 时序真相。

**提取方法备忘**（复用价值高）：EFI 内嵌 initramfs=gzip 魔数（1f 8b 08）且解出 070701 cpio 的段；注意内核里有多个假魔数（字符串表/xz 压缩表），需实际解压验证。

## 2.5 v8/v9 观察者实测（2026-10-22 深夜，initramfs 修复后重跑）

**时序铁证**（v8，三处 pr_info 时间戳）：
```
1.505  PANEL_PREPARE_ENTER          ← panel prepare 先跑
1.533  exit sleep -22 + Failed to initialize panel（probe 失败）
1.533  DSI_PRE_ENABLE → POWER_ON    ← dsi 上电反而在后（各跑两次）
```
**结论**：panel prepare 早于 DSI host power_on 30ms——transfer 检查 `msm_host->power_on=false` 返回 -EINVAL。

**机制定位**（v9+源码离线）：panel bridge 的 prepare 在 `drm/bridge/panel.c:129 panel_bridge_atomic_pre_enable`（atomic 阶段由 KMS commit 调）；msm dsi 的 power_on 在自己 bridge 的 pre_enable（dsi_mgr_bridge_power_on）。**两者都是 bridge 链成员，执行顺序=链顺序——时序证据表明 panel bridge 排在 msm dsi bridge 之前（顺序反了）**。正常设计：dsi bridge 先（power_on+内部也调 prepare）→ panel bridge 后（幂等跳过）。

**v10 修法方向**：①查 msm dsi bridge 链构建（attach next 顺序）修正为 dsi 先 panel 后；②或 panel bridge pre_enable 前确保 host power on；③或 panel prepare 对 -EINVAL 有限重试（次优）。

**另发现（独立问题）**：a630_zap.mbn 缺失（GPU zap shader，原厂可提）→ adreno init 失败 → DPU SMMU context fault 洪水（SID 0xc88/0x880）——不影响 panel 结论，出帧前要补。

## 2.6 突破：-22 修复成功（v13，2026-10-23 00:20，无人值守）

**完整因果链定案**：drm bridge chain 的 pre_enable 语义=**从链尾向链头反向执行**（drm_bridge.c:839 注释）→ panel bridge（链尾）先跑 prepare，dsi bridge（链头）后跑 power_on → transfer 撞 `power_on=false` → -22。**修复=一行**：panel 驱动 probe 里 `ctx->panel.prepare_prev_first = true`（该字段经 panel_bridge 转写为 bridge 的 `pre_enable_prev_first`，drm 官方为"DSI host 需先于外设初始化"设计——woaiyuzi 移植时漏设）。

**v13 实测判决**（三路观察者）：
```
1.479  v13: prepare_prev_first=true
1.502  DSI_POWER_ON（先）
1.531  BRIDGE_PRE_ENABLE → PANEL_PREPARE（后）
1.577  RDID[fresh]: 0x04=0x07 DA=0x07 DB=0x00（rc=1 读取成功）
1.713  RDID[after-on]: 0x04=0x40（display on 正常）
```
-22 消失、exit sleep 成功、init 序列完整下发、**背光节点在**（brightness=204/max=4095）、DRM connected、msmdrmfb、panel/dsi 零错误。

**屏 ID 读出**：DA=0x07 DB=0x00（第三方屏）→ **勘误（2026-10-23 00:30 对表）**：v13 树内的 init 序列经核对**已与原厂序列一致**（EF 8字节版/D5=0x14/d2 扩展组/fc 5a5a 全部相同——副会话移植时已对过原厂参数；§7 说的"7 处差异"是对比 woaiyuzi 6.5 原版，对象搞错）——**无需换序列**。原厂序列存档仍有价值（doze/ACL/HBM 组可后续补）。

**后续待办**：①a630_zap.mbn 固件补齐（修 SMMU fault 洪水，出帧质量相关）②用户醒来物理确认屏幕显示 ③充电轮 SMB2 实验可合并下一轮刷写。

**历史包袱清算**：v11（atomic wrapper）无效是因为 flag 是实例字段非 funcs 字段；v12 发现 mainline 已支持（由 panel->prepare_prev_first 驱动）；v13 设置即通。

## 7. 屏幕断电保护轮（v48-v52，2026-10-24 00:30-02:30）——物理损坏屏的硬件断电

**需求**：屏体物理损坏（红蓝斑纹/闪 milogo）→ 用户要求切断屏幕供电保护硬件，只改一个值、保留 DRM 链路。

**弯路（软件假账本教训）**：
- v48 `panel@0 status=disabled`：Linux 不再接管 → **UEFI 开的 LAB/IBB/WLED 成遗留状态，regulator 账本与硬件脱钩**——sysfs 显示 disabled 但硬件仍供电；regulator_force_disable(v50 内核 hack)、backlight 强关、GOP 12MB 清零（写落验证过）全部"软件成功、物理无效"
- **用户洞察定案**："屏幕没被 Linux 接管所以软件不生效" ✓

**正解（v51+v52）**：
1. v51：panel 恢复 okay（DRM 正规接管，账本同步——实测接管后 lab/ibb 立即变 enabled=真状态）
2. v52：**ea8074 panel 驱动 probe 末尾调用 `ss_notch_fhd_ea8074_unprepare(&ctx->panel)`**（msleep(500) 后）——框架正规关断（reset 释放+regulator_bulk_disable）
3. **最终证据**：lab=disabled/ibb=disabled（同步真账本）+ backlight actual=0 + 用户目视全黑 ✓
4. 开机行为：milogo（UEFI 数秒）→ Linux 接管 → panel 短暂 init → ~1.5s unprepare 断电 → 保持全黑
5. **换屏恢复**：删 panel-samsung-ea8074.c 里的 `MI8: damaged panel` hack（3 行）+black-screen.service 保留背光兜底，重编即回显示能力
6. 辅助资产：fbcon=map:16（内嵌 cmdline，开机不画 Tux，v49）；black-screen.service v2（关背光+12MB GOP 清零+fbcon 解绑）
7. 附带红线：**DRM 接管前对 display regulator 的一切软件操作均不可信**（账本脱钩）；DPMS sysfs 只读；msm-mdss 无 runtime PM 目录

三轮版本与结局对照：

| 版本 | exit sleep 失败后 | RDID read | 结局 |
|---|---|---|---|
| 1930 cmd（V1） | **return 中断** | 未执行 | **系统活着**（SSH 通，DRM bind/connected） |
| tolerant v1 | 继续 | **提前到最前** | 挂死（三路全失） |
| tolerant v2 | 继续 | 还原到 exit sleep 后 | 挂死 |
| tolerant v3 | 继续 | **完全去掉** | 挂死 |

**改判结论**：挂死真凶 = **exit sleep 失败后继续执行 init 序列本身**（set_page_address / vendor DCS 序列 / display on-off 链中的某条 transfer 在 host 未就绪阶段挂死内核），**不是 RDID read**。V1 的安全来自"第一失败即 return"。用户目击佐证（V1 时代）：UEFI 正常 → 企鹅（efifb）→ 闪一下（msm-drm 接管+panel reset）→ 黑屏卡死（init 失败，DPU 帧到不了面板）——系统活着。
另注：v2 时代"全黑+背光不亮"= prepare 失败后 unprepare 断 LAB/IBB 供电。

**屏幕攻坚 v4 之前的方向**：msm dsi host 的 cmd transfer 在 panel prepare 阶段的 enable 时序（`msm_host->enabled` 置位点 vs drm_panel_prepare 调用点）——需读 6.19 `dsi_host.c`/`dsi.c` 的 enable 链 + 对照 edk2 的 host/PHY 配置；或 panel 驱动内延迟/重试机制。**v4 策略=回到 V1 行为保稳定，屏幕转专门课题。**

## 3. 编译管线经验（本轮新坑）

2. 工具前台超时会连带杀 WSL 编译；后台 `wsl.exe` 常驻则 make 存活（proc 后台 + notify 模式可行）。
3. 拼 EFI 断言链复用副会话脚本（MZ 头 + FDT 魔数精确落在 Image 长度处 + dtb 尾完整）。

## 4. 恢复手册（用户醒后，按序）

设备现状：ESP 里是挂死的 tolerant 内核（85d9eaab），开机即卡（黑屏/无 USB/无串口）。

1. **长按电源 10 秒关机** → 再开机若仍卡死 → 进 **fastboot（音量下+电源）**。
2. **fastboot 修 ESP**（若分区表有 esp）：
   `fastboot flash esp 03-备份/锚点-20261022-0040/02-配置层/esp-full-20261022.img`（314MB 全量备份，写回即回 #48+旧 EFI 状态）。
   若 fastboot 无 esp 分区 → 方案 C。
3. **UEFI shell 兜底**：开机音量上+电源（若 edk2 出 shell）：`fs0:` → `rm EFI\Boot\BOOTAA64.EFI` → 从备份复制回。
4. **U盘**：FAT32 U盘放 `\EFI\BOOT\BOOTAA64.EFI`（用 `06-安装包/BOOTAA64-20261021.efi`=#48 版）——edk2 扫所有块设备。
5. 恢复判据：SSH（10.55.0.1 或 169.254.1.1）+ `dmesg | head` 可读。恢复后**把 ESP 里 EFI 换回 #48**（`mount -o rw /dev/sda22 /mnt/esp` + cp）再重启，回到 WiFi 修复后的稳定态。
