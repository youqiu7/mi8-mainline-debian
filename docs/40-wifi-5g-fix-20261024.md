## 1. 现象与证据链（全部实机取证）

- 关联层一切正常：auth/assoc/EAPOL 全成功、`CTRL-EVENT-CONNECTED`，信号 -57~-64dBm。
- **数据面死**：静态 IP 时代网关 ARP `INCOMPLETE`；改 DHCP 后拿不到租约；curl 全失败。
- **抓包定性（tcpdump，已装 4.99.6+libpcap1.11）**：
  - 出站：DHCP DISCOVER/ARP request 已发出（tx failed=0）。
  - 入站：**只收得到其他客户端的广播/组播**（.134 mDNS、.151 SSDP、.180 mDNS）——**广播下行通**。
  - 网关（192.168.10.1=OPPO A5 路由器）对本机一切单播请求无回应（OFFER/ARP reply 全丢）。
  - 5G 时 `rx bitrate` 恒 6.0M；2.4G 关联即 243–270M MCS14/15。
- **分水岭实验（决定性）**：连同一路由器的 2.4G 频段 "OPPO A5" → DHCP 一次成功（.248/.249）、网关 ARP REACHABLE、百度 200/60ms、70s 循环 30/30 零断线。
- key `failed to install key ... -110`：**社区定案为 ath10k 已知良性 GTK rekey 超时**（ath10k@infradead msg16873、HA 同款日志），非根因。

## 2. 根因判定（把握度分项）

**判定：5G 高速率 RX 失效（组播/管理帧走 6M 能收，AP 对单播用中高速率下发即全丢）。**

| 假设 | 把握度 | 依据 |
|---|---|---|
| 5G 边缘信号 + 无设备校准 BDF（generic board-2.bin，board_id 0xff）导致 RX 灵敏度崩 | **60%** | dmesg `board_id 0xff` 与 postmarketOS M0Rf30/wcn3990-regdomain 项目定案完全吻合（WCN3990 系列全部用 generic BDF 无 per-device 校准）；-64dBm 属边缘；26 号验收"5G 通"可能当时信号/信道更好 |

## 5. 新增踩坑记录（并入 24 号手册族）

1. **oneshot 服务等"后出现的设备"会阻塞整个 multi-user.target**：wifi-regdom 等 wlan0 → multi-user 不达成 → `After=multi-user.target` 的 mss-start 推迟 → wlan0 更不出现（26 号 device-unit 阻塞的同型坑，第 2 次踩）。铁律：**任何 multi-user.target.wants 的 oneshot 必须秒完成**；等设备用 udev RUN。
2. **驱动开机默认 PS=on**（ath10k_snoc/v54 实测）——服务器必须 udev 强制 off。
3. **ARP complete ≠ 双向通**：内核被动学习任何 ARP 帧 sender 即 complete；判定双向必须主动请求+回应（本轮曾据此误判"boot 早期通"）。
4. ath10k `key -110` = 已知良性（GTK rekey 超时 3s），别再当根因查。
5. 设备无 ping/wget，只有 curl；测网络用 `curl -m N -w`。
6. WCN3990 无设备校准（board_id 0xff generic BDF）是这代机型的社区共性（postmarketOS 多机型同款）。

## 7c. 5G 修复攻坚（15:45–16:35 增量，用户明确要求修 5G 而非禁用）

**用户修正（重要）**：①"OPPO A5"只是路由器自定义名，**与 OPPO 品牌无关**；②**两台 AP 均 WiFi6 (AX)**（路由器 + Redmi K70 Pro 热点）；③Redmi 5G 连上后**几秒闪断**（用户观察，我 27s 测试窗内未捕获）。**共同变量修正为：5G 频段 × AX AP × WCN3990(WiFi5) 客户端**；2.4G 上同样的 AX 向后兼容却完全稳定。

**客户端实验矩阵（全部完成）**：

| 参数 | 合法性（parse 验证） | 结果 |
|---|---|---|
| 默认 | — | 关联成功、组播通、单播死（5/5 确定性） |
| `disable_vht=1` | 合法 | **auth 阶段即失败**（两轮复现），且 auth 失败循环会引发**固件 wedge**（下条） |
| `disable_ht` 系 | 同类判死刑 | 未再试 |
| `disable_ampdu=1` | **非法字段**（此 wpa build） | 实验无效（wpa 解析崩溃重启循环） |
| `disable_max_amsdus=1` | **非法字段** | 同上（parse 先行验证拦住，无害） |
| `ieee80211w=1` | 合法 | 关联成功、**MFP: yes**、单播依然全死 → PMF 非病根 |

**新机理两例实锤**：
1. **固件 wedge**：auth 连续失败数次（如 disable_vht 触发）→ WCN3990 TX 假死 → **所有 AP（含手机热点）auth 零回应**，软件不可恢复，**仅整机 reboot 解开**（两次复现；remoteproc stop 禁用——26号硬重启教训）。**这就是用户"彻底连不上、要重启"型故障的机理**，另一会话 13:29-13:38 的 restart 风暴会造成同样效果。
2. **disable_vht 毒性**：带宽能力类参数改变 chandef 通告，触发 auth 失败→wedge 链。

**固件/物料查证**：
- board-2.bin = firmware-atheros_20250410 同尺寸（670116）→ **已是 2025 最新 BDF**，升级无增量。
- WLAN 固件（WLAN.HL.2.0.c3，2019 build）**锁死在原厂 wlanmdsp.mbn 内**（26号 modem 配对校验约束），**不可单独升级**——"2019 固件 × 2020+ AX AP"时代差嫌疑存在但软件无解。
- 工具链沉淀：**wpa_supplicant 字段合法性验证法** = `timeout 3 wpa_supplicant -c test.conf -i fake0 -Dnl80211`（parse 先于 bind，假接口零干扰）；设备无 col/man 可读时用此法。

**结论：客户端 wpa 层修复路线穷尽**。剩余修复面（按证据强度）：
1. **路由器侧三选一**（1 分钟，最对症"WiFi5×AX 5G"）：AX 模式→AC 模式 / ch52→36 或 149 / 160MHz→80MHz
2. **Redmi 热点 5 分钟长窗口取证**（连上不主动断，抓闪断瞬间 reason code——区分 AP 踢 vs 本地 key 错误，进一步钉死机理）
3. 长线：wpa -dd 全 debug + ath10k trace（无 ATH10K_DEBUG config，突破概率低）

## 7d. Redmi 长窗口取证（16:35–16:43，用户选路径 2）

**实录**：16:35:36 关联 5805/ch161 + 4-way 完成 → **稳定 5 分钟**（其间测速：下行 108KB/s，但 PHY 866.7M 顶格/-35dBm/零重传——瓶颈=手机蜂窝上游，空口健康）→ **16:40:33 本地断开 reason=4（链路失效/beacon loss 型）** → 16:40:34–16:41:55 重连挣扎（每 8s 一轮 auth→assoc→超时，进不了 CONNECTED，CONN_FAILED 累积）→ **16:42:27–58 坏状态污染 2.4G**（3 轮失败）→ 16:43+ 自行恢复。热点信道在窗口内从 5745 漂到 5805（ch161）。

**两层病理定性**：
1. **Redmi（手机热点）闪断** = 稳定数分钟后 beacon loss 型断链——主嫌疑**手机热点省电踢人**（Android 热点息屏/空闲降发射；待用户"亮屏保持热点"复测判别）；断后固件坏状态+恢复挣扎（2019 固件健壮性差）。
2. **路由器 5G 单播死**（ch52/160M/AX）= 独立的确定性病（5/5），客户端无解。
3. **共性**：5G 数据路径坏状态会污染 2.4G（同一固件）——"WiFi 整体时好时坏"的体验来源；坏状态多数可自行恢复，严重时 wedge 需 reboot（§7c）。

**待决**：①用户亮屏复测判别热点省电；②路由器三选一（AX→AC/ch 换/160→80M）。

## 7e. 终局：v56b 驱动层修复成功（17:00–17:55，用户拍板"从固件/系统层面解决"）

**白盒取证（v55，ATH10K_DEBUG=y）**：
- debugfs 武器库解锁（fw_dbglog/pktlog/wmi_services/simulate_fw_crash/tpc/reg_value…），但**固件的 HTT RX 统计段即使 DEBUG 也全 0**（2019 量产固件不实现上报）、fw_dbglog 无输出——统计路死。
- **WMI_SERVICES 金矿**：`BLOCKACK -`（显示口径，2.4G 140Mbps 实测证明聚合功能在）、`PACKET_POWER_SAVE/ADVANCED_PWRSAVE enabled`、`BCN_MISS_OFFLOAD enabled`。
- 2.4G 吞吐实测 17.5MB/s（140Mbps）→ 聚合全局健康 → 差异收敛到 **VHT**：2.4G(HT40) 健康 / Redmi(VHT80) 短暂通 / OPPO(VHT160) 全死 → **2019 固件 VHT 数据路径缺陷**（QCA 后期固件才修复；固件被 modem 配对锁死不可升级——§7c 考古）。

**v56 驱动 patch**（mac.c，`ath10k_mac_setup_ht_vht_cap`）：
```c
static bool ath10k_disable_vht;
module_param_named(disable_vht, ath10k_disable_vht, bool, 0644);
/* 函数内 */ if (ath10k_disable_vht) vht_cap.vht_supported = false;
```
cmdline `ath10k_core.disable_vht=1`（CONFIG_CMDLINE_FORCE 内嵌）→ wiphy 注册时不通告 VHT → AP 以 HT20/40 关联 → 绕开固件 VHT 死路。与 wpa 层 disable_vht 的本质区别：源头禁（固件从一开始就按 HT 配置，无能力不同步）。

**两次编译踩坑（并入手册）**：
1. `module_param(disable_vht,...)` 要求变量名即参数名——变量叫 `ath10k_disable_vht` 必须用 `module_param_named(disable_vht, ath10k_disable_vht, bool, 0644)`，否则 clang 报 undeclared identifier。
2. **内建驱动 cmdline 参数前缀 = KBUILD_MODNAME**：ath10k 的内建模块名是 **ath10k_core**（/sys/module/ 只有 ath10k_core），写 `ath10k.disable_vht=1` 会被**静默忽略**（未知 cmdline 参数不报错）——正确为 `ath10k_core.disable_vht=1`。判据：sysfs 参数文件不存在即前缀错。
