## 三、关键结论（踩过的坑，别再踩）

### 3.1 `dtb=` 参数会让内核 panic ★最重要

- 23:43 第一次成功时，cmdline **没有** `dtb=`，内核用 **UEFI 提供的 polaris DTB**
  （`/proc/device-tree/model` 显示 `Xiaomi Mi MIX 2S`）
- 之后我为了"修正 DT model"加了 `dtb=/equuleus.dtb`，让内核从 ESP 读自己编译的 dtb
- **结果：之后每一次启动全黑、无 USB、无 COM**，即使用完整 dtb（138,570 / reserved-memory=23）
- 推断原因：UEFI 的 DTB 是**固件启动时动态修补过的**（chosen/framebuffer/reserved-memory 运行地址），
  ESP 里的是静态编译产物；`efi_load_dtb()` 用它替换修补版 → 内核 early boot 死掉
- **结论：不要用 `dtb=`，接受 `DT model` 显示兄弟机型**

### 3.2 `fastboot boot` 引导内核无效

- `fastboot boot <内核 boot.img>` 在本机**从未成功出过 COM**（ABL 的 appended-DTB 路径不通）
- **只有 UEFI 路径能引导内核**：`fastboot boot boot-equuleus.img` 或 `adb reboot recovery`
- 之前十几轮用 `fastboot boot` 测内核，全部无效，导致误判"内核坏了"

### 3.3 UMS 写入不可信

- `cp` 到 UMS 的 `E:` 盘后立刻 `md5sum` 会通过（读 Windows 页缓存）
- 设备端实际没收到 → ESP 一直是旧文件
- **必须**：adb 写入 + **设备端** `su -c md5sum` 校验

### 3.4 dtb 生成漏参数会丢 reserved-memory

- `cpp` 漏 `-I scripts/dtc/include-prefixes` 或 `dtc` 漏 `-@`
- → dtb 只剩 1 个 reserved-memory（应 23 个）→ 内核覆盖保留内存 → panic
- **每次生成 dtb 必须验证**：`dtc -I dtb -O dts | grep -c reserved-memory` 应为 23

### 3.5 路径陷阱（Windows / WSL / MSYS 三套）

| 场景 | 正确路径 |
|---|---|
| Windows git-bash（terminal 工具）| `/e/EFI/Boot/` |
| WSL 内 | `/mnt/e/`（但 **UMS 盘 WSL 看不到**）|
| 传变量给 WSL | **必须写成 .sh 文件**，`wsl -c '...$VAR...'` 会吞变量 |

### 3.6 回滚必须比对 md5

- 同一个大小（39,716,510）对应两份不同内容（init v3 = `3e4ef13c`，init v4 = `fa316ed2`）
- 我多次拿错版本当"基线"，导致"回滚了也不工作"的假象

## 四、下一步：init v5（switch_root 进 Debian）

**⚠️ 动 init 之前必须跑校验脚本**：`02-工具/55-verify-before-v5.sh`（见下节）

### 计划步骤

1. **校验**（只读）：确认 sda23 的 rootfs 完整可用（见第五节清单）
2. **编译 init v5**：`04-实验/p3/init_v5.c`（含 `try_switch_root()`）
3. **重编内核**：EXT4 保持 `=y`，cmdline 仍**无** `dtb=`，INITRAMFS_SOURCE 指向 init v5
4. **拼接**：Image + appended dtb 138,398
5. **写 ESP**：adb + 设备端 md5
6. **UEFI 引导**：`adb reboot recovery`
7. **验收**：串口应出现 systemd 启动日志 → Debian login

### init v5 的关键逻辑

```c
need_ums = access("/dev/sda23", F_OK) ? 1 : 0;
if (!need_ums) {
    mk("/newroot");
    need_ums = (mount("/dev/sda23", "/newroot", "ext4", MS_RDONLY, NULL) != 0);
    if (!need_ums) umount("/newroot");     // 只是探测
}
setup_gadget(..., need_ums);                // 串口永远配
...
if (try_switch_root() == 0) return 0;       // mount + pivot_root + exec /sbin/init
// 失败 → 诊断模式（UMS + 串口）
```

**风险点**：`mount("/dev/sda23", ...)` 若 UFS 层卡死，init 会停在 mount 上，串口永不出现。
这正是之前怀疑过的地方——但当时 **sda23 是空的**，现在已写入完整 ext4，mount 应该会很快成功。
