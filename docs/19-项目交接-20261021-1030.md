## 三、WiFi 攻坚全景

### 已闭环结论（勿重复工作）

1. **根因链已修正**：原"SDM845 DTS 缺 IPCRTR 传输节点"判定错误；真实根因是 modem 未启动。modem 启动后 IPCRTR/SSM_RTR/glink_ssr rpmsg 设备全部出现。
2. **UEFI 不用换**：Mindows 同源（Renegade Project edk2-msm，bootaa64.efi.mindows=1.7MB 为 bootmgfw 备份）。实机引导用 UEFI 内置 polaris DT（103,588B，edk2-msm FdtBlob 下 dipper/equuleus 均复用 sdm845-xiaomi-polaris.dtb），**我们拼装的 equuleus-wifi.dtb 从未生效**——不要再花时间改我们的 dts。
3. **upstream mba.mbn 被 PBL 拒绝**（status -284557301）——必须用原厂 mba（238,304B，来自 03-备份/bk_modem.img FAT 分区）。
4. **CONFIG_QRTR_NS 不存在**（Kconfig 无此符号）——不要再开。
5. **skip-quirk 补丁已应用**（David Heidelberg v5 三文件 backport 到 6.19.14）：Poco F1/LG G7 同固件家族需 skip host-cap QMI；**Kali bug #9767 铁证 polaris 需此 quirk 修 'msa info req rejected: 90'**。
6. **电源/时钟提前使能 patch 已落地**（snoc.c probe 内 regulator_bulk_enable + clk_bulk_prepare_enable），实测 5 路 vdd 全 enabled、rf_clk2=1。
7. **固件布局**（pmOS 确认与实测一致）：ath10k/WCN3990/hw1.0/{board-2.bin,firmware-5.bin,wlanmdsp.mbn}；上游 20260319 包已无 qcom/sdm845/wlanmdsp.mbn 全局链接，但 hw1.0 目录三件套齐全（wlanmdsp.mbn 3,725,044B）。

### 当前卡点（wlanfw 不注册的排查状态）

- **QRTR 机制源码级确认**：qmi_add_lookup 是本地 socket（node0→ns），**LOOKUP 不依赖 IPCRTR 传输**；WCN3990 的 REGISTER 需要 IPCRTR 就绪后到 ns → ns 遍历 lookup → 推 server arrive。理论上链路已通。
- **qmi_send_new_lookup 无错误检查**：LOOKUP 一定发出（本地），ns 一定收到。
- **结论**：ns 侧机制完好 → 唯一解释是 **WCN3990 固件（ROM）从未在 QRTR 注册 wlanfw** → 上电条件仍差一环。

### ⭐ 最新铁证（组织者调研 85% 中间结论，接手机后的头号方向）

**Baryshkov《WCN399x pwrseq》v3 已上游 Applied**（官方解法）：
- **新增 qcom,wcn3990-pmu 节点，强制先 VDD_IO（1.8V ldo7）再其它电压**（0.8→1.8→1.3→3.3 时序）
- 我们当前是 **regulator_bulk_enable 同时开 5 路**——**极可能违反 WCN3990 上电时序，导致 ROM 起不来/不注册 wlanfw**
- **6.19.14 源码未含 WCN3990 的 pwrseq 支持**（pwrseq-qcom-wcn.c of_match 仅 qca6390/wcn6750/wcn6855/wcn7850，**无 qcom,wcn3990-pmu**）→ 官方新供电方案不适用本机，换 DT 加节点也不匹配 → **只能驱动侧自研顺序上电**
  - 方案 A（驱动侧，首选，论证见 `19b-WCN3990上电时序论证-20261021.md`）：snoc.c probe 改为**顺序 enable**：先 vdd-1.8-xo（ldo7，XO 1.8V）→ usleep 50-100ms → 其余 4 路 → usleep → 再 clk。**当前数组顺序 cx(0.8V) 先于 xo(1.8V) 且无延时，疑似违反 1.8V 先行要求**
  - 方案 B（换 DT 加新节点）：6.19 驱动不匹配，弃
- **参考**：JlW 子代理报告结论"上游 snoc.c 设计不存在 probe 期等 FW_READY 死锁；hw_power_on 在 wlan_enable 之前"——与我们 patch 的"probe 提前上电"并不冲突，但正式语义应是在 wlan_enable 时才上电。我们的 patch 已在 probe 提前给电（更早），顺序（bulk 同时、cx 先行）才是问题。

   - 再 clk enable（现状）；失败路径逆序 disable
