## 1. 内核选型：从 6.5 改为 6.19.14（就地取材）

原计划用 `woaiyuzi/linux`（6.5-rc4，含 dipper DTS + EA8074 面板驱动）。
实际执行时 GitHub clone 在 WSL 里卡在 2 MB 不动（CN 网络），于是改成：

| | |
|---|---|
| 内核 | **本机已有的 `/root/k619/linux-6.19.14`**（WSL Debian） |
| 工具链 | `aarch64-linux-gnu-gcc` 14.2.0（Debian） |
| 配置基线 | `01-资料/pmos-dipper-pkg/config-xiaomi-dipper.aarch64`（pmOS 给 dipper 调过的完整 config） |

**为什么可以这样换**：P1 的目标是「内核进 userspace + 屏幕出日志」，只需要 simplefb，**不需要面板驱动**。
面板驱动（P2 才需要）仍然是 6.5 那份，届时按 6.19 的 DRM API 适配或用 `linux-mdss-dsi-panel-driver-generator` 重新生成。

## 2. DTS：`04-实验/p1/sdm845-xiaomi-equuleus.dts`

派生自 dipper DTS，改动集中在四处：

| 改动 | 内容 | 依据 |
|---|---|---|
| 身份 | `model = "Xiaomi Mi 8 UD (equuleus)"`、`compatible = "xiaomi,equuleus"` | 实测 DT model |
| board-id | `<79 0>` / msm-id `<321 0x20001>`（**与 dipper 相同，原样保留**） | 实测 |
| 电池 | 4,000,000 → **3,000,000 µAh** | 实测 `charge_full` |
| **simplefb** | `chosen/framebuffer@9d400000`，1080×2248，stride 4320，`a8r8g8b8`；`reserved-memory` 里加 `cont_splash_region`（**不加 no-map**，否则 simplefb 映射不到） | `xbl_a` 的 "Display Reserved" |

**P1 显式关闭的节点**（这是「一次只改一个变量」的落地）：
```
&mdss &mdss_dsi0 &mdss_dsi0_phy &dispcc &gpu &gmu      ← 显示/GPU，让 simplefb 独占
&adsp_pas &cdsp_pas &mss_pil &venus &ipa &wifi          ← 需要固件的 remoteproc
&pmi8998_fg                                             ← 6.19 里这个 label 不存在
```

**保留**：UFS（rootfs）、USB（peripheral 模式调试）、PMIC 供电、gpio-keys、sdhc_2、uart6。

## 3. 编译过程与三个坑

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | `make dtbs` 死在 `sa8155p-adp.dtb`：找不到 `dt-bindings/clock/qcom,dispcc-sm8150.h` | 本机源码树不完整（缺无关机型的头文件），全量 dtbs 会把无关板子也编译 | 只编我们的 dtb：`cpp + dtc` 手工两步（见 `05-build-dtb-manual.sh`），绕过 make 的 dtbs 依赖 |
| 2 | `gcc: unrecognized command-line option '-mlittle-endian'` | **忘了 `CROSS_COMPILE`**，Kbuild 用 host gcc 编了 aarch64 目标 | `make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- ...`，并先 `mrproper` 清掉 x86 的 .o |
| 3 | `Label or path pmi8998_fg not found` | 6.19 的 `pmi8998.dtsi` 里没有 fuel gauge 节点（pmOS 6.5 有） | DTS 里删掉 `&pmi8998_fg` 整段，电量留到 P4 |

另外发现：**第一次 make 出来的 `arch/arm64/boot/Image` 是 10-19 遗留的旧产物**（时间戳 21:19 而编译 21:31 才开始，且失败中断），差点拿去打包。教训：产物必须核对版本串与时间戳。

## 4. initramfs

不用 busybox，直接写一个静态链接的 C `init`（`04-实验/p1/init.c`）：
- 挂载 proc/sys/devtmpfs
- 打印 `uname`、`/proc/device-tree/model`、`/proc/cmdline`、`/sys/class/drm/version`
- 打印 `EQUULEUS P1 INITRAMFS 已接管`
- 20 次心跳（每 2 秒），然后关机

产物：`/root/k619/p1-initramfs/initramfs.cpio.gz`（289,560 B，6 条目，`gzip -t` 通过，init 为 ELF 静态）

## 6. 实机测试：**被 USB 掉线阻塞**

执行过程：
```bash
adb -s 225bd9ea reboot bootloader     # 返回成功
sleep 12; fastboot devices            # 空
```

随后连续观察 2 分钟：

| 通道 | 结果 |
|---|---|
| `adb devices` | 空 |
| `fastboot devices` | 空（`fastboot -s 225bd9ea getvar` 一直 `< waiting for 225bd9ea >`） |
| Windows PnP（全部 USB VID） | **没有任何手机设备**：无 `VID_18D1`(Google)、无 `VID_2717`(Xiaomi)、无 `VID_05C6`(Qualcomm) |
| 异常设备（Status != OK） | 无（不是驱动问题，是 USB 根本没枚举） |

**判定**：设备已从 USB 完全消失，三种可能：
1. 停在 fastboot 界面但 USB 栈没起来（少见）
2. 已经关机（电量 89%，不太可能）
3. 数据线/端口接触问题（`adb reboot` 后重新枚举时掉了）

**需要人工确认**（我在远端无法按键）：
1. 看屏幕：是 fastboot 的米兔界面？还是黑屏？还是 MIUI 开机动画？
2. 长按电源 10 秒强制重启，看是否能回 Android
3. 换一根线 / 换一个 USB 2.0 口，再 `adb devices`

**回滚安全性**：`fastboot boot` 从未执行，`boot`/`recovery` 分区一个字节都没写，`03-备份/` 完整。**当前设备状态与测试前完全一致**。
