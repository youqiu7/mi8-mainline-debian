## 3. 调研结果本地核验（源码级，WSL 6.19.14）

### 3.1 Baryshkov 补丁系列实况
- 系列：`[PATCH v3 0/8] Bluetooth, wifi, arm64: extend WCN driver to support WCN399x device`（2026-01/04，Dmitry Baryshkov @oss.qualcomm.com）
- 3/8 `wifi: ath10k: snoc: support powering on the device via pwrseq`：`devm_pwrseq_get(&pdev->dev, "wlan")` 走**通用 power sequencing 框架**，DT 需 `qcom,wcn3990-pmu` 节点
- **但**：6.19.14 `drivers/power/sequencing/pwrseq-qcom-wcn.c` of_match 表只有：
  - `qcom,qca6390-pmu`（8 路 vreg：vddio 第一）
  - `qcom,wcn6855-pmu`（10 路：vddio 第一）
  - `qcom,wcn7850-pmu`（7 路：vdd 第一、vddio 第二）
  - `qcom,wcn6750-pmu`（7 路：vddaon 第一）
  - **无 `qcom,wcn3990-pmu`** → 官方新供电方案**未覆盖 WCN3990**
- v3 还有已知问题：CONFIG_POWER_SEQUENCING=n 时 pwrseq_get 返回 -ENOSYS 致 probe 失败（Luca Weiss 报告，20260418 已有修复帖）

### 3.2 结论：官方 pwrseq 路线对本设备不可用
即使换 DT 加 qcom,wcn3990-pmu 节点，6.19.14 驱动也不匹配（无此 compatible）→ 需再 backport 评审中补丁 + 换 DT 双重成本 → **放弃该路线，回到驱动侧自研顺序上电**。

### 3.3 支持"1.8V 先行"的证据
- 新芯片 pwrseq desc 普遍将 **vddio（1.8V IO）列第一**，且带 `pwup_delay_ms=50~60` + gpio 延时
- Baryshkov 动机：WCN399x 内置简单 PMU 扩展电压 → IO/振荡器 rail 必须先于后级电压
- 硬件合理性：XO 振荡器（1.8V）需先稳定，后级（0.8 核/1.3 射频/3.3 电荷泵）由 PMU 从 XO/IO 电源生成

## 4. 我们的现状 vs 假设

snoc.c probe patch（已部署，md5 525c27a5）：
```c
regulator_bulk_enable(num_vregs, vregs);   // 数组顺序: cx(0.8) → xo(1.8) → rfa(1.3) → ch0(3.3) → ch1(3.3)，无延时
clk_bulk_prepare_enable(num_clks, clks);   // cxo_ref_clk_pin + qdss
```
- **vdd-1.8-xo（XO 电源）是第二个，0.8V cx 反而最先，且无任何延时**
- 与 §3.3 证据冲突（1.8V 应最先 + 有 pwup 延时）→ **本次论证锁定的头号嫌疑**

### 动作 A 实施细节（本地已可准备，手机回来后部署）
1. 改 snoc.c 1783 处：拆 `regulator_bulk_enable` 为顺序使能：
   - 先 `regulator_enable(vregs[1])`（vdd-1.8-xo = VDD_XO/IO）→ `usleep_range(50000, 100000)`（参照 pwup_delay 50ms 量级）
   - 再逐个 enable vregs[0]（cx）→ vregs[2]（rfa）→ vregs[3]/[4]（ch0/ch1）→ `usleep_range(50000, 100000)`
   - 再 clk enable（保持 vdd→clk 顺序，现状不变）
   - 失败路径：逐个 disable（逆序）
2. 重编 → 拼 EFI → 写 ESP（记录新 md5）→ 重启 → 验证：wlanfw 注册？wlan0 出现？
3. 判定：
   - wlanfw 注册 → 根因坐实（时序），继续 wlan0/连接流程
   - 不注册 → 转假设 B（rf_clk2 输出验证），不再盲目重复 A
