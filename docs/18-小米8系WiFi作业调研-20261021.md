## 0. TL;DR（最高信号结论）

1. **没有"一键整机镜像 + 安装脚本"式的完整现成 Debian/Arch 移植作业**，但存在被社区反复验证的成熟路径：**edk2-msm UEFI + 主线内核 + 自制 rootfs**，步骤可整体借鉴（见 §2.6 清单）。
2. **铁证：UEFI 给小米8 加载 polaris dtb 是构建期绑定的**——`dipper.fdf.inc` 第 20-22 行明文嵌入 `FdtBlob/sdm845-xiaomi-polaris.dtb`；`equuleus.dsc` 直接复用 `dipper.fdf.inc`；2301.1 的 boot-dipper.img 与 boot-polaris.img 字节数完全相同（6662144）。**换 dtb 只能"构建时换"，运行时无任何覆盖机制**——不要再往 EFI 尾部拼 dtb 试错（§2.1）。
3. **上游主线（torvalds/linux）与 Renegade 的 linux-snapdragon 都没有 dipper/equuleus/ursa 的 dts**，SDM845 小米系只有 beryllium（Poco F1）与 polaris（MIX 2S）两份。唯一在推进的是：David Heidelberg 2026-09 提交的"Mi 8 family compatibles"上游化补丁（评审中，已查到邮件线程）+ sdm845-mainline MR !102（Draft，未合并）。本机实机 DT 的 wifi 节点与 Renegade 打补丁版 polaris.dts **逐字一致**（5 路 vdd + `qcom,snoc-host-cap-skip-quirk` + okay）（§2.2、§2.3）。
4. **前提修正（重要）**：上游 snoc.c 的时序是**先 `ath10k_hw_power_on()` 供电、再 `ath10k_snoc_wlan_enable()`（QMI + 等 FW_READY）**，probe 中的 `ath10k_qmi_init()` 只注册 QMI lookup、**不阻塞等待**。"core_register 依赖 wlanfw FW_READY 造成循环依赖"这一表述**在主线源码层面不成立**；实机 ldo5/7/23 未使能，更可能是 **hw_power_on 根本没被跑到（core_start 未到达 / probe 链更早失败）**，需用 dmesg 时间线定位（§2.4）。但"让芯片在 QMI 交互前有电"的修复方向不变：dts always-on / probe 早 enable / 官方 pwrseq，三条路都成立。
5. **官方解已合入上游**：Dmitry Baryshkov（高通）的 WCN399x pwrseq 系列（v3，2026-01-19，维护者回复 "Applied, thanks!"）——新增 `qcom,wcn3990-pmu` 节点 + `drivers/power/sequencing/pwrseq-qcom-wcn.c`，ath10k-snoc 优先走 `pwrseq_power_on()`，旧 5 路 regulator 模型保留为 fallback。**本机 6.19.14 大概率已含该框架代码**（需本地确认 snoc.c 是否有 `devm_pwrseq_get`，见 §3-P0）；polaris dtb 没有 wcn3990-pmu 节点，所以仍走旧的 regulator 回退路径（§2.4）。
6. **最小可抄动作**：参照 upstream polaris（sdm845-mainline 7.1-dev）给 pm8998 的 `vreg_l17a_1p3`(ldo17)、`vreg_l25a_3p3`(ldo25) 补 `regulator-always-on`（本机这两路实测已 enabled，可延伸给 l5a/l7a/l23a 补上做对照实验）；固件部署按 §2.5 布局（Debian `firmware-atheros` 包即可覆盖 WCN3990）。
7. **社区实况**：没有任何人在"edk2-msm + 主线 Linux"组合上让小米8 出过 wlan0（edk2-msm 的 wifi issue 全是 Windows 场景）；Renegade legacy 矩阵标 equuleus WiFi=Y/BT=Y/LTE=Y 是 **5.18 时代口径**，不能直接照搬到 6.19（§2.6、§4）。

## 2. 详述

### 2.1 UEFI 内置 dtb 机制：为什么是 polaris、能否换

**铁证一（构建脚本）**：`dipper.fdf.inc`（edk2-msm master）第 20-23 行：

```
// Mainline device tree blob
FILE FREEFORM = 25462CDA-221F-47DF-AC1D-259CFAA4E326 {
  SECTION RAW = Platform/Xiaomi/sdm845/FdtBlob/sdm845-xiaomi-polaris.dtb
}
```

**铁证二（equuleus 复用）**：`equuleus.dsc` 关键行 `DEVICE_DXE_FV_COMPONENTS = Platform/Xiaomi/sdm845/dipper.fdf.inc`——屏下指纹版直接搬 dipper 的 FV，只改 `PcdDeviceProduct|"MI 8 UD"` / `PcdDeviceCodeName|"equuleus"` 给 UEFI 自己显示用。

**铁证三（目录与二进制）**：
- `Platform/Xiaomi/sdm845/FdtBlob/`（进 UEFI 给主线 Linux 用的小 dtb，94-103KB）**只有 `sdm845-xiaomi-beryllium.dtb`(94069B) 和 `sdm845-xiaomi-polaris.dtb`(103382B)**，没有 dipper/equuleus 主线 dtb。
- `FdtBlob_compat/` 里的 `dipper.dtb`/`equuleus.dtb`（各 494189B）是**下游 Android dtb**，不是给主线 Linux 的——这就是"EFI 尾部拼 equuleus dtb 不生效"的另一层原因：即便拼上，那也是主线不认的 Android 板级 compatible。
- 2301.1 release 资产：boot-dipper.img = boot-polaris.img = **6662144 字节完全相同**；boot-equuleus.img = 6660096。
- 从仓库下载的 polaris.dtb 解析出 model="Xiaomi Mi MIX 2S"、compatible="xiaomi,polaris","qcom,sdm845"、wifi@18800000(compatible qcom,wcn3990-wifi)、mss firmware "qcom/sdm845/polaris/modem.mbn"——与本机 /sys/firmware/fdt（103588B, model="Xiaomi Mi MIX 2S"）吻合（103382 vs 103588 的 206B 差异推断为 UEFI 侧 FDT 补全，未逐字节验证）。

**能否换 dtb**：
- **运行时换：无机制**。FREEFORM dtb 的 GUID（25462CDA-…）编译期绑定，UEFI DXE 只认 FV 里那一份；Renegade wiki/issues 无"从 ESP/存储读 dtb 覆盖"、"启动菜单选 dtb"能力。结论：**不要再往 EFI 尾部拼 dtb**。
- **构建时换（有路径）**：自写 dts → dtc 编译 → 放入 `Platform/Xiaomi/sdm845/FdtBlob/` → 改 `dipper.fdf.inc` 第 22 行 `SECTION RAW` → 按 README/build.sh 重新 build → `fastboot boot boot-dipper.img`。注意：**换 dtb 只解决 model 字符串/板级节点问题，修不了 WiFi 供电卡点**（WiFi 时序问题在驱动/DT 电源节点侧）。
- 上游 edk2-msm `Platform/Xiaomi/sdm845/` 只有 `equuleus.dsc` 与 `perseus.dsc`（没有 dipper.dsc）——equuleus 是 Renegade UEFI 的一等公民，2301.1 即最后一个多设备正式版。

### 2.3 skip-quirk 是什么、为什么必须保留

上游补丁（Amit Pundir / David Heidelberg，v4 2026-03-25，给 beryllium 加 skip-quirk）原文："The Wi-Fi firmware used on Xiaomi Poco F1 (beryllium) phone doesn't support the host-capability QMI request, so add a quirk to skip it on this device."（https://lists.infradead.org/pipermail/ath10k/2026-March/016872.html ）

- 即：小米系 WCN3990 固件不支持 host-capability QMI 请求，缺这个 quirk 时 ath10k 会收到拒绝（Kali #9767 记录 polaris 报 "msa info req rejected: 90"）。
- 本机 DT 已带此 quirk（源自 Renegade），**保留，不要删**。若换用自写 dts，务必带上。

### 2.4 供电时序真相与官方解法（针对"循环依赖"前提修正）

**上游 master snoc.c 时序（已查证原文）**：

```c
// probe 路径：只 get，不 enable，不阻塞
ar_snoc->pwrseq = devm_pwrseq_get(&pdev->dev, "wlan");   // 拿不到(EPROBE_DEFER)回退旧 5 路
ar_snoc->num_vregs = ARRAY_SIZE(ath10k_regulators);        // 无 pwrseq: =5；有: =1
ret = devm_regulator_bulk_get(&pdev->dev, ar_snoc->num_vregs, ar_snoc->vregs);  // 只 get
...
ret = ath10k_qmi_init(ar, msa_size);   // 只注册 QMI lookup，无 wait_for_completion
return 0;

// hif_power_up（core_start 路径）：先供电、再 QMI、再等 FW_READY
ret = ath10k_hw_power_on(ar);                              // pwrseq_enable(1029) → regulator_bulk_enable(1033) → clk(1037)
ret = ath10k_snoc_wlan_enable(ar, fw_mode);                // QMI wlan_enable，内部等 FW_READY
```

结论：**主线设计上"供电 → QMI wlan_enable → 等 FW_READY"顺序正确，probe 期不等待固件**。若实机在等待 FW_READY 时 ldo5/7/23 仍未使能，说明 **hw_power_on 从未执行**（core_start 未到达，probe 链或 core worker 更早失败），或 polaris dtb 与该内核驱动不匹配——需要 dmesg 时间线定位（§3-P0），而不是把问题归为"驱动时序缺陷"。

**官方解法（Baryshkov pwrseq 系列，v3 2026-01-19 Applied）**：
- 动机原文："WCN39xx … incorporate a very simple PMU on die … it also requires a certain start-up procedure (**first bring up VDD_IO, then bring up other voltages**)"。
- 改动：`ath10k_hw_power_on()` 里 `pwrseq_power_on()` 先于 `regulator_bulk_enable()`；probe 有 pwrseq 时 num_vregs=1；`pwrseq-qcom-wcn.c` 定义 WCN3990 target（无独立 BT/WLAN enable GPIO，vddio→vregs→clk，pwup_delay 50ms）。
- 已切换板卡：db845c、OnePlus 6/6T（master 已见新模型 dts）；**polaris 未切**——所以本机即便 6.19.14 内核有 pwrseq 框架，DT 没描述 PMU 节点仍走旧路径。
- 对应内核配置：`CONFIG_POWER_SEQUENCING` 与 `CONFIG_REGULATOR_QCOM_WCN`（pwrseq-qcom-wcn.c）。

**对本机卡点的综合判断**：用户"probe 期提前 bulk_enable"的补丁 ≈ pwrseq 思路的手动版，方向合理；但它绕过了上游设计（上游本就先供电再 QMI），所以更应先确认 **hw_power_on 是否被跑到**、以及 regulator phandle 是否真的对应到 pm8998 的 ldo5/7/23（polaris DT 中 ldo 定义与 wifi 节点 phandle 的对应关系需在实机 /sys/kernel/debug/regulator 复核）。

### 2.6 引导方式对比与现成作业

**引导方式**：
- pmOS（5.12 时代）：SDM845 机型不走 lk2nd，用原厂 ABL + `fastboot flash boot boot.img`，dtb 按 mkbootimg 约定拼在 boot.img 尾部；内核包同时产 vmlinuz.efi（ZBOOT，EFI 引导可用）与 gzip vmlinuz。→ 该推断由 APKBUILD 打包方式 + 同代 beryllium 惯例反推，**置信度中高**（wiki 正文被反爬未读到）。
- 本机（Renegade 路线）：UEFI 从 FV 内 FREEFORM 取 dtb（§2.1），与 ABL 路径不同——**ABL 阶段的电源遗留状态可能与 pmOS 路径不同**，这是"pmOS 当年能跑通、本机不行"的一个候选解释（未验证）。

## 3. 可执行借鉴项（按优先级，标注适用条件）

> 适用基线：本机 DT = polaris（wifi 5 路 vdd + skip-quirk + okay；mss polaris 路径已 running），内核 6.19.14，UEFI 2301.1。

**P0 —— 先验证前提（免费，10 分钟内完成）**
1. 本地内核源码确认：`drivers/net/wireless/ath/ath10k/snoc.c` 是否有 `devm_pwrseq_get` 与 `pwrseq_enable` 行（有 = 6.19 已含官方框架，缺 = 版本早于 pwrseq 合入线）。grep 即可。
2. dmesg 时间线：搜 `ath10k_snoc` probe 是否返回 0；是否打印 "soc power on"（snoc.c hw_power_on 内的 dbg 行）。**若 "soc power on" 从未出现 → 问题在 core_start 之前（probe 链/modem init/msa 内存区/QMI 注册），不是供电**；若出现后 ldo 仍为 0 → 查 rpmh-regulator 是否被 edk2 锁住、或 dts 中 ldo5/7/23 的 phandle 是否真对应 pm8998 那几路（`/sys/kernel/debug/regulator` 复核）。
3. 复核"循环依赖"表述：确认 6.19.14 的 qmi.c `ath10k_qmi_init` 是否非阻塞（对照 master 行为）。

**P1 —— dts 供电兜底（最小改动，可热验证）**
- 参照 upstream polaris（sdm845-mainline 7.1-dev）给 pm8998 的 `vreg_l17a_1p3`、`vreg_l25a_3p3` 补 `regulator-always-on`（本机实测这两路已 on，此步是补全语义）；若仍卡，延伸给 `vreg_l5a_0p8`、`vreg_l7a_1p8`、`vreg_l23a_3p3` 补 always-on 做对照实验。
- 注意：pmOS/equuleus 当年 l5/l7 没加 always-on 也跑通（推断靠 ABL 遗留供电），说明 always-on 不是唯一路径；本机路径不同（UEFI），所以值得先试。
- 改法：**不要动 EFI 尾部拼 dtb**；两条路任选：(a) 按 §2.1 构建时换 dtb 重打包 boot 镜像（需要重新 build edk2-msm）；(b) 内核命令行用 dtbo/overlay 手段（若 6.19 的 qcom overlay 支持）——优先 (a) 已验证路径。

**P2 —— 官方 pwrseq 新模型（长期正确解，工作量中等）**
- 抄 db845c/OnePlus 的 `qcom,wcn3990-pmu` 节点（§2.2 模板）加进 polaris dts 的 wifi 节点旁，wifi 节点 4 路改指 `vreg_pmu_xo/rf/ch0/ch1`，`vdd-0.8-cx-mx` 保留 `<&vreg_l5a_0p8>`；vddio 仿 db845c 用 fixed always-on（vreg_s4a_1p8 或本机对应 1.8V rail）。
- **⚠ swctrl-gpios 引脚未验证**：db845c/OnePlus 用 `pm8998_gpios 3`，小米主板引脚未必相同，对照原理图前勿直接照抄（可先去掉该属性测试）。
- 内核配置：`CONFIG_POWER_SEQUENCING`、`CONFIG_REGULATOR_QCOM_WCN`。
- 这样 ath10k-snoc 会走 `pwrseq_power_on()`，由 pwrseq 驱动保证 VDD_IO 先于其它电压，从机制上消除"必须外部先上电"的依赖；**用户已写的 probe 提前 bulk_enable 补丁可作临时验证手段，但应同时核对关机/remove 路径的对称 disable，避免 PMIC 轨常开耗电**。

**P3 —— 固件部署确认（对照 §2.5）**
- 确认 `/lib/firmware/ath10k/WCN3990/hw1.0/{board-2.bin, firmware-5.bin, wlanmdsp.mbn}` 存在（Debian `firmware-atheros` 包）；确认 `qcom/sdm845/wlanmdsp.mbn` 符号链接存在；board-2.bin 用默认 variant（equuleus 未设 calibration-variant，勿加 beryllium 校准串）。
- mss 固件路径保持 polaris（已 running），不要改成 equuleus 的 `qcom/sdm845/mi8/`。

**P4 —— 若仍坚持"正确 dtb"（构建时换，步骤见 §2.1）**
- 以 beryllium-common + Renegade polaris wifi/mss 节点为模板自写 dts（参考 MR !102 与 David Heidelberg 补丁线）；**换 dtb 不解决 WiFi 供电卡点**，只解决 model 字符串/板级节点。

**P5 —— 社区调试套路（现成作业借鉴）**
- Renegade Arch 教程串的通用套路：固件进 initramfs（mkinitcpio BINARIES 填 zap/ipa_fws 路径）、pd-mapper/tqftpserv/qrtr/rmtfs 服务、USB 网卡 ssh（10.15.19.82 段）补救——WiFi 未通前这是保持远程调试能力的标准做法。

**全局提醒**：`qcom,snoc-host-cap-skip-quirk` 必须保留（§2.3）；不要照抄 equuleus 的"4 路缺 ch1"（2021 年简化配置，upstream 现为 5 路）。
