# 小米 8 屏幕指纹版 (equuleus / SDM845) 移植 Debian 13 — 总体规划与实施路径

> 版本 v1.0 · 2026-10-20 · 状态：前期准备完成，等待决策点确认后进入 P1
> 本项目所有结论均基于**本机实测**，取证命令与原始输出见 `02-硬件取证报告.md`。

## 0. 结论先行（TL;DR）

| 结论 | 依据 |
|---|---|
| **可行性：高**。这是 SDM845 平台，主线 Linux 支持是 2018 年机型里最好的之一 | 主线 6.19 已有 beryllium(Poco F1)/polaris(Mi Mix 2S)/OnePlus6 等 20+ 台 SDM845 设备 |
| **但"开箱即用"不存在**：equuleus 没有主线 DTS，屏幕(EA8074)与触摸(ST FTS)驱动都不在上游 | 已核对 torvalds/linux master、sdm845-mainline sdm845-6.11、pmaports 官方包 |
| **有利条件远多于 dagu 项目**：已解锁、vbmeta 已空、dtbo 已空、Magisk 可 root、有 60 GB 闲置分区、board-id 与 dipper 相同 | 见 §2 |
| **推荐路线**：Debian 13 rootfs + 自建内核，内核起步用 `woaiyuzi/linux` (6.5-rc4，含 dipper DTS + EA8074 面板驱动)，稳定后 rebase 到主线 | §3 |
| **推荐分区方案**：把闲置的 `mindowswin`(59.7 GiB) 格式化为 ext4 当 Debian 根分区，**保留 Android**，Linux 的 boot 放进 `recovery` 分区 | §4 |
| 预计总工时 | 2–3 周（业余节奏），其中屏幕点亮是唯一的"未知项" |

## 1. 目标与范围

**目标**：在这台 equuleus 上跑起 Debian 13 (arm64) + GNOME/Wayland 桌面，达到可日常使用的程度，并产出可复现的安装包 + 文档（沿用 dagu 项目的交付标准）。

**验收线（分级）**
- **M1 能启动**：串口/USB 网络可见，内核进 userspace，SSH 可登录
- **M2 能看见**：屏幕点亮（先 simplefb 兜底，再上 DRM 面板驱动）
- **M3 能操作**：触摸可用、WiFi 可用、能装桌面进图形界面
- **M4 能日常**：音频、亮度、充电/电量、suspend、OTG 基本可用
- **M5 可交付**：分层锚点备份 + 一键安装包 + 覆盖对照文档

**明确不做（本阶段）**：屏下指纹（goodix FOD，主线无解）、摄像头、通话/短信、NFC、Windows 共存。

## 2. 硬件与软件基线（实测）

### 2.1 设备身份
| 项 | 值 | 取证 |
|---|---|---|
| 型号 | MI 8 UD（小米 8 屏幕指纹版），M1807E8A | `ro.product.model` / `ro.boot.cert` |
| 代号 | **equuleus** | `ro.product.device` |
| DT model | `Xiaomi Technologies, Inc. Equuleus MP v2.1` | `/proc/device-tree/model` |
| SoC | SDM845，`qcom,msm-id = <321 0x20001>` | `/proc/device-tree/qcom,msm-id` |
| **board-id** | **`<79 0>`（0x4f）** | `/proc/device-tree/qcom,board-id` |
| 内存 / 存储 | 7.4 GiB / UFS 114.5 GiB | `/proc/meminfo`, `/proc/partitions` |
| 系统 | MIUI 12.5.2.0.QECCNXM / Android 10 / 内核 4.9.186 | `getprop` |
| Root | **Magisk 已装，`su` 直接可用** | `su -c id` → `u:r:magisk:s0` |

> ⭐ **board-id 79/0 与上游 dipper DTS 中的 `qcom,board-id = <79 0>` 完全相同**。这意味着 dipper 的 DTS 可以近乎直接复用，不必从零推算 bootloader 匹配值。

### 2.2 显示与输入
| 项 | 实测值 | 影响 |
|---|---|---|
| 面板 | `dsi_ss_ea8074_notch_fhd_cmd_display`（三星 EA8074，1080×2248，**cmd mode**，刘海） | 需要 panel 驱动；`woaiyuzi/linux` 里的 `panel-samsung-ea8074.c` 正是从同族 vendor DT 生成的 `ss_notch_fhd_ea8074` |
| 触摸 | **STMicroelectronics FTS**，`st,fts`，I2C14(`a98000`) 地址 `0x49`，INT=GPIO31 / RST=GPIO32 | 上游 `stmfts.c` 只认 `st,stmfts`，**需加一行 compatible** |
| 其它 I2C | `atmel_mxt_ts_640u@4a`、`ndt@50`/`ndt@72`（压感） | 非必需，可延后 |
| 指纹 | goodix FOD（SPI） | **不做** |

### 2.3 分区布局（A-only，单槽）
| 分区 | 设备 | 大小 | 现状 |
|---|---|---|---|
| boot | sde45 | 64 MiB | Android 4.9 内核，header **v1** / page 4096 |
| recovery | sda19 | 64 MiB | MIUI 恢复；**可作为 Linux boot 的落点** |
| dtbo | sde37 | 8 MiB | **全 0（已被擦空）** |
| vbmeta | sde8 | 128 KiB | **全 0（已验证链断开）** |
| userdata | sda21 | 55,664,620 KiB ≈ **53.1 GiB** | ext4，已用 25 GiB（Android 数据） |
| mindowsesp | sda22 | 307,204 KiB ≈ 300 MiB | Mindows 残留 ESP（FAT32） |
| mindowswin | sda23 | 62,607,352 KiB ≈ **59.7 GiB** | Mindows 残留 Windows 盘（NTFS） |
| modem | sde46 | 192 MiB | **ADSP/CDSP/venus/modem 固件的来源** |
| system / vendor | sde48 / sde47 | 3 GiB / 1 GiB | Android |

### 2.4 引导链现状（关键）
- `abl_a` 开头是 **`\177ELF`** → 仍是**原厂 ABL**，不是 Mindows 的 UEFI（之前装过 Mindows，引导器已刷回，但 Windows 分区留下了）
- `ro.boot.verifiedbootstate=orange`、`flash.locked=0` → 已解锁
- `dtbo` 与 `vbmeta` 分区**全为 0** → AVB 验证链已断，**刷任意 boot.img 不会被拒**
- 串口：`console=ttyMSM0,115200n8 earlycon=msm_geni_serial,0xA84000`，UART 电压 1.8 V（对应 pmOS wiki 的 Mi8 UART 测试点图）
- `ramoops_memreserve=4M` → pstore 可用，崩溃日志可回溯

> 结论：**这台机器的刷写门槛比 dagu 低得多**。没有 AVB 拦截、没有双槽回退逻辑、没有"bootloader 拒绝非原厂 header"的强校验。

## 3. 路线论证：为什么是"Debian + 自建内核"

### 3.1 三条候选路线

| | A. postmarketOS 官方包 | **B. Debian 13 + 自建内核（推荐）** | C. Mindows/UEFI |
|---|---|---|---|
| 现状 | pmaports **有 `device-xiaomi-equuleus`**（device/testing），依赖 `linux-postmarketos-qcom-sdm845` **6.11** | 需自建 | 曾被装过，分区还在 |
| 致命缺口 | 该 6.11 内核树里**没有** `sdm845-xiaomi-equuleus.dts`（已核对 Makefile：只有 beryllium/polaris），也没有 EA8074 面板驱动 → 装了也点不亮 | 要自己写 DTS | ABL 已被刷回原厂，重装 UEFI 风险高；且主线内核在 UEFI 下缺 DTB/驱动配套 |
| 系统 | Alpine + Phosh | **Debian 13 + GNOME（用户目标）** | Windows |
| 结论 | 只当**参考实现**（deviceinfo 偏移值、soc-qcom-sdm845 依赖清单 rmtfs/pd-mapper/tqftpserv 很有用） | **主线** | 放弃 |

### 3.2 内核选型（三选一，附实测依据）

| 内核树 | 版本 | equuleus/dipper DTS | EA8074 面板驱动 | ST FTS 触摸 | 用途 |
|---|---|---|---|---|---|
| `torvalds/linux`（本机 WSL 已有 **6.19.14**） | 6.19 | ❌ 无 dipper/equuleus | ❌ 无 | ✅ `stmfts.c`（仅 `st,stmfts`） | 最终归宿 |
| `sdm845-mainline/linux` tag `sdm845-6.11` | 6.11 | ❌ 无（只有 beryllium/polaris） | ❌ 无 | ✅ | pmOS 用的树，作对照 |
| **`woaiyuzi/linux` main** | **6.5.0-rc4** | ✅ `sdm845-xiaomi-dipper.dts` | ✅ `panel-samsung-ea8074.c`（结构体名 `ss_notch_fhd_ea8074`，与本机面板同款） | ✅ `stmfts.c` | **起步基准** |

**决策**：P1 用 `woaiyuzi/linux` 6.5 起步（拿到 DTS + 面板驱动的最小可用组合），把 DTS 改成 equuleus；等 M4 达成后再考虑 rebase 到 6.19 主线（那时补丁集已经从我们的工作里沉淀出来）。

> 已归档到 `01-资料/woaiyuzi-linux/`：`panel-samsung-ea8074.c`、`stmfts.c`、`sdm845-xiaomi-dipper.dts`、`panel-Makefile`、`dts-Makefile`、`k-Makefile`。

### 3.3 equuleus 相对 dipper 必须改的 DTS 差异

| 项 | dipper DTS 现值 | equuleus 实际 | 依据 |
|---|---|---|---|
| 触摸 | `focaltech,ft8719` @ i2c14 0x49 | **`st,fts`** @ i2c14 0x49（同地址同 GPIO） | vendor DT `i2c@a98000/fts@49` |
| 电池 | `charge-full-design-microamp-hours = <4000000>` | **3000000**（2999 mAh 实测） | `/sys/class/power_supply/*/charge_full` |
| 音频 | 外挂 `tas2557` @ i2c5 0x4c | vendor DT 无 tas 节点，`/proc/asound/cards` = `sdm845-tavil-snd-card`（WCD9340 直驱） | dmesg + asound |
| model | `Xiaomi Mi 8 (ea8074)` | `Xiaomi Mi 8 UD / equuleus` | DT model |
| 面板 | `samsung,ea8074` | 同族，但本机是 **notch** 变体 → 优先用 `ss_notch_fhd_ea8074` 的初始化序列 | `msm_drm.dsi_display0=dsi_ss_ea8074_notch_fhd_cmd_display` |
| board-id/msm-id | `<79 0>` / `<321 0x20001>` | **完全一致，不改** | 实测 |

## 4. 分区与"双系统"方案论证

### 4.1 三个候选

| 方案 | 做法 | 风险 | 回滚 |
|---|---|---|---|
| **① 回收 Mindows 分区（推荐）** | `mke2fs` 格式化 `sda23`(59.7 GiB) → Debian 根；Linux boot 写入 `recovery`(64 MiB)。开机「音量上+电源」进 Linux，「电源」进 Android | 极低：不动 GPT、不动 userdata、不动 boot | 刷回 `recovery` 原镜像即恢复原状 |
| ② 覆盖 userdata（dagu 老路） | userdata 全给 Debian | 中：Android 与数据全没 | 重新刷 MIUI |
| ③ 改 GPT 加分区 | `sgdisk` 缩小 userdata 后新建 | 高：分区表写坏=全盘丢失 | 只能 EDL 全盘回读恢复 |

**推荐 ①**。理由：
1. `sda23` 是**已存在的独立分区**，只需要 `mkfs.ext4`，**不需要改分区表**——这是本项目最大的风险规避点；
2. Android 侧不挂载它，格式化不影响 Android 的 `/data`；
3. `recovery` 分区本就是 MIUI 恢复（可随时从原厂包刷回），拿来放 Linux boot 是 SDM845 单槽设备的经典做法；
4. 单槽设备没有 `fastboot --set-active` 可用，切换系统只能靠分区落点区分——`boot` vs `recovery` 正好是两套独立引导路径。

**代价（必须明确）**：
- Android 的 OTA/恢复功能会失效（recovery 被 Linux 占用）
- 切换系统要靠按键，不能从系统内一键切换
- 60 GB 是全部可用空间，没有"再扩"的余地

### 4.2 目录/文件落点规划
```
sda23  (mindowswin, 59.7 GiB)  →  ext4  →  Debian 根分区
                                         PARTLABEL 建议改名为 debian-root（可选，需写 GPT，延后做）
recovery (64 MiB)              →  Linux boot.img (kernel 30~45 MB + initramfs ~10 MB)
boot    (64 MiB)               →  保持 Android 原样（不动）
dtbo / vbmeta                  →  保持空（已空，反而是优势）
modem   (192 MiB)              →  Debian 只读挂载，取 adsp/cdsp/venus/modem 固件
```

### P1 — 内核起得来（1–2 天）
- 建 `sdm845-xiaomi-equuleus.dts`（从 dipper DTS 派生，按 §3.3 改）
- **第一版目标只有一个：simplefb + fbcon 起来**。`&mdss`/`&mdss_mdp`/`&gpu`/`&dispcc` 全部 disabled，屏幕直接继承 bootloader 的 splash framebuffer，cmdline 加 `console=tty0 fbcon=map:0` —— 这样**屏幕本身就是控制台**，替代 UART（见 §8.1）
- 打包 boot.img（`Image.gz` + dtb 拼接，参数见 §6），`fastboot boot` 试引导（失败不落盘，重启回 Android）
- 失败后**先读 pstore**（`/sys/fs/pstore/console-ramoops-0`），再决定改什么
- **门槛**：`fastboot boot` 后屏幕（或 172.16.42.1 的 SSH）出现内核日志，能进 initramfs shell

### P2 — 屏幕与触摸（3–7 天，风险最高）
- 上 `mdss` + `dsi0` + `panel-samsung-ea8074`（notch 初始化序列）
- 触摸：`stmfts.c` 加 `{ .compatible = "st,fts" }`，核对 GPIO/中断/供电
- **门槛**：桌面可见 + 触摸可点；否则退回 simplefb 保底

### P3 — 系统落地（2–3 天）
- Debian 13 arm64 rootfs（debootstrap 或现成镜像）写入 `sda23`
- 网络三选一：USB gadget(172.16.42.1) / WiFi(WCN3990，需 rmtfs + pd-mapper + tqftpserv) / 串口
- 时间同步（无 RTC，`fake-hwclock` + `timesyncd`，dagu 已踩过坑）
- **门槛**：SSH + apt 可用，重启后自恢复

### P4 — 外设（3–5 天）
亮度（pmi8998 WLED）→ 电量/充电 → 音频（WCD9340 + UCM）→ suspend → OTG

### P5 — 交付（1–2 天）
分层锚点（config / boot / rootfs 各自独立备份）+ 安装包 + 覆盖对照文档 + 遗留问题清单

## 6. 已就绪的工具与关键参数

### 6.1 mkboot_v1.py（已写好并通过往返测试）
`02-工具/mkboot_v1.py`，固定使用本机实测的 boot.img 参数：

```
magic ANDROID! | header_version 1 | page_size 4096
kernel_addr 0x00008000 | ramdisk_addr 0x01000000
second_addr 0x00f00000 | tags_addr   0x00000100
os_version  0x1400014c | header_size 1648 | recovery_dtbo_size 0
```

**往返测试结果**：把原厂 `boot` 分区解包再重打包，`header(除 id 字段)+kernel+ramdisk` 与原厂 **逐字节一致（0 差异）**。
唯一差异是 header 里 32 字节的 `id`（SHA-1 摘要）——小米的算法与 AOSP `update_sha()` 不同。**该字段 bootloader 不校验（vbmeta 已空），无功能影响**。
> 这比 dagu 那套 v3 header 简单得多：这里没有 `vendor_boot`、没有 page_size 陷阱、没有 `vendor_ramdisk_size` 偏移问题。

### 6.2 打包主线的正确姿势（Nura 主线指南 + 实测参数吻合）
```bash
cat Image.gz sdm845-xiaomi-equuleus.dtb > /tmp/kernel-dtb
python 02-工具/mkboot_v1.py pack \
  --kernel /tmp/kernel-dtb --ramdisk initramfs.cpio.gz \
  --cmdline "console=ttyMSM0,115200n8 earlycon=qcom_geni root=PARTLABEL=debian-root rootwait rw" \
  -o boot-linux.img
```
- 内核必须 **`Image.gz`**（原厂也是 gzip），dtb 用 `cat` 直接拼在 kernel 后（不是 v3 的 `--dtb`）
- `dtbo` 已空 → **不需要** `fastboot erase dtbo` 这一步（pmOS/Nura 指南里那步对本机已是既成事实）

### 6.3 探索期专用命令（不落盘）
```bash
fastboot boot boot-linux.img      # 只引导不写入；失败重启即回 Android
fastboot flash recovery x.img     # 正式落点
fastboot flash boot     x.img     # 危险：会顶掉 Android 引导
```

## 7. 风险登记表

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | EA8074 **notch** 变体的初始化序列/porch 与 dipper 不同 → 黑屏或半屏 | 中 | 高 | 先 simplefb 保底；用 `linux-mdss-dsi-panel-driver-generator` 从**本机 vendor DT** 生成驱动（本机 DT 可 dump） |
| R2 | `st,fts` 与上游 `stmfts` 的寄存器/固件加载流程有差异 → 触摸无响应 | 中 | 中 | 只加 compatible 先试；不行再对照 MIUI 的 `fts_ts` 驱动移植（源码可从 LineageOS device tree 找） |
| R3 | 刷错 `boot` 分区导致 Android 起不来 | 中 | 中 | **P0 必做**：64 MiB boot 已备份（`03-备份/boot_equuleus_原厂.img`，md5 `c7da48be…`），一条 `fastboot flash boot` 即回滚 |
| R4 | 降级原厂固件触发 anti-rollback 变砖 | 低 | **致命** | **铁律：不降级 MIUI 大版本**，保持 V12.5.2.0 (Android 10) |
| R5 | `mindowswin` 里还有用户想留的 Windows 数据 | 中 | 中 | 格式化前先确认；建议先只读挂载看一眼 |
| R6 | WiFi 需要 `rmtfs`+`pd-mapper`+`tqftpserv` 才能工作，缺一个就连不上 | 高 | 中 | 照抄 `soc-qcom-sdm845` 包依赖；UART/USB gadget 作为备用通道 |
| R7 | 无 RTC，时间错位导致 apt HTTPS 全挂（dagu 踩过） | 高 | 低 | 首启脚本第一条就 `date -s` + `fake-hwclock` |
| R8 | UFS 分区 sector size 4096，rootfs 镜像必须按 4096 对齐 | 中 | 中 | `mkfs.ext4 -b 4096`，rootfs 用 4096 sector 构建 |
| R9 | **无 UART**，早期 hang 完全不可见（D3 决定不拆机） | 中 | 高 | ①simplefb+fbcon 优先于 DRM；②每轮失败先读 `/sys/fs/pstore/console-ramoops-0`；③一次只改一个变量；④只用 `fastboot boot`，不落盘 |
| R10 | 占用 `recovery` 后 Android 的 OTA/恢复不可用 | 确定发生 | 低 | 原厂 `recovery.img` 已备份，随时可刷回；Android 日常使用不受影响 |

## 8. 决策点（已确认 / 待定）

| # | 问题 | 决定 | 影响 |
|---|---|---|---|
| **D1** | Android 要不要保留？ | ✅ **保留**。回收 `sda23`(59.7 GiB) 做 Debian 根，Linux boot 写入 `recovery` 分区；开机「音量上+电源」进 Linux，「电源」进 Android | 分区方案锁定为 §4 方案①；`userdata` 与 `boot` 一律不动 |
| **D2** | `mindowswin` 里的 Windows 数据还有用吗？ | ✅ **无重要数据，可以格式化**。P3 直接 `mkfs.ext4` 覆盖 `sda23` | 分区方案完全解锁，P3 无前置阻塞 |
| **D3** | 拆机接 UART？ | ✅ **不拆**。只靠 USB 网络 + simplefb 兜底 | 见下方「无串口调试策略」——P1 的设计要围绕它调整 |
| **D4** | 第一版桌面 | ✅ **Phosh** | P3 装 Phosh；GNOME 作为后续可选升级 |
| **D5** | 原厂 ROM | ✅ 用户自行解决，不用我处理 | 回滚链仍以 `03-备份/` 为主 |

### 8.1 无串口调试策略（因 D3 = 不拆机，必须提前设计）

没有 UART 时，早期的眼睛只有三个，按可靠性排序：

1. **fbcon（最重要）**：simplefb 一旦绑上，把 `console=tty0` 加进 cmdline，内核日志就直接滚在屏幕上——**效果等同于串口**。所以 P1 的第一版必须优先保证 simplefb 起得来，而不是先追求 DRM 面板。
   cmdline 建议：`console=tty0 console=ttyMSM0,115200n8 fbcon=map:0`
2. **pstore/ramoops**：本机 cmdline 有 `ramoops_memreserve=4M`，panic/挂死前的日志会留在内存里，**重启回 Android 后可直接读**：
   ```bash
   adb shell "su -c 'ls -la /sys/fs/pstore/'"
   adb shell "su -c 'cat /sys/fs/pstore/console-ramoops-0'"
   ```
   这是"盲刷失败后唯一的事后证据"，每轮失败必须先读它再改。
3. **USB gadget**：initramfs 自带的 usbserial/rndis → `172.16.42.1`。但它要等 initramfs 跑起来，救不了早期 hang。

**因此 P1 的铁律**：每次只改一个变量；`fastboot boot`（不落盘）失败后**先读 pstore**，不要在看不见的情况下连续改。

## 9. 与 dagu 项目的复用关系

**可直接复用**：

- `pack_dagu_p0.py`（那是 boot header **v3** + vendor_boot 的打包器；米 8 是 **v1**、无 vendor_boot）→ 已另写 `mkboot_v1.py`
- dagu 的双槽切换思路（米 8 是**单槽**）
