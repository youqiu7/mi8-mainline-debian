## 1. 进度定位（精确到环节）

**WiFi 链路环节链**：WCN3990 芯片上电 → ROM 注册 wlanfw(QMI) → ath10k server arrive → host_cap → msa 分配 → 固件上传 → FW_READY → core_register → core_start(hif_power_up: 正式供电+QMI) → wlan0

| 环节 | 本机状态 | 依据 |
|---|---|---|
| modem/mss | ✅ running | remoteproc0=running（原厂 mba/modem） |
| WCN3990 外部供电（5 路 LDO） | ✅ enabled | 我们 probe 提前 enable patch（ldo5/7/17/23/25 全 enabled） |
| cxo_ref_clk | ✅ enable_count=1 | rf_clk2 |
| WCN3990 固件三件套 | ✅ 补齐 | board-2.bin + firmware-5.bin + wlanmdsp.mbn |
| QRTR 命名服务 / IPCRTR | ✅ | ns.o 内置（af_qrtr.c:1299）；glink-edge.IPCRTR rpmsg 存在 |
| **WCN3990 ROM 注册 wlanfw** | ❌ 未发生 | qrtr 无服务、ath10k 无 dmesg |
| ath10k 后续整链 | ⏸ 未启动 | 依赖 server arrive |

**问题精确表述**：WCN3990 芯片内 ROM 未在 QRTR 注册 wlanfw 服务 → server arrive 之后的整条链从未启动。**外部供电与时钟已满足，故卡点收窄到"WCN3990 芯片自身的启动条件"**。

## 2. 组织者调研对旧认知的修正（已本地核验）

### 2.1 "循环依赖"表述在主线源码层面不成立（组织者 C5 + 本地核验）
- snoc.c 上游流程：probe 只 `devm_regulator_bulk_get`（不 enable）→ `ath10k_qmi_init`（只注册 lookup，非阻塞）；供电在 `ath10k_hw_power_on`（snoc.c:1019，带 "soc power on" dbg 打印）→ 由 `ath10k_snoc_hif_power_up`(:1076) 调用 → hif_power_up 在 `ath10k_core_start`（core.c:2977）→ `ath10k_core_probe_fw`（register_work:3509）→ FW_READY 事件后的 register_work 调度（core.c:3501-3524）。
- 即：上游假设 **WCN3990 在 Linux probe 之前已有电**（ABL/bootloader 遗留供电），Linux 到 core_start 才正式接管。
- **对本机含义**：edk2-msm UEFI 不做 Android 式板级供电 → 无遗留电 → **我们 probe 提前 enable 的 patch 必要性依然成立**（组织者 TL;DR 第 4 条：让芯片在 QMI 交互前有电的修复方向不变）。

### 2.2 pwrseq 官方路线对本机不可用（组织者 C6 + 本地核验修正 19b）
- 组织者推断"6.19.14 大概率已含 pwrseq 框架"——**本地核验修正**：6.19.14 的 `pwrseq-qcom-wcn.c` of_match 只有 qca6390/wcn6750/wcn6855/wcn7850；**ath10k snoc.c 无任何 devm_pwrseq_get 接入**（全文件 grep 0 命中）→ **本机内核走旧 5 路 regulator 模型，pwrseq 路线不可用**（既无驱动接入也无 DT 节点），不要再考虑换 DT 加 wcn3990-pmu。
- 但官方补丁的**动机文字是铁证**："WCN39xx … requires a certain start-up procedure (**first bring up VDD_IO, then bring up other voltages**)"——**1.8V 先行**是本芯片族硬性启动条件。

### 2.3 换 dtb 只此一条路且修不了供电（组织者 C1/C10，已铁证）
- dipper.fdf.inc:20-23 构建期嵌入 polaris dtb；equuleus.dsc 复用 dipper.fdf.inc；2301.1 boot-dipper/boot-polaris 字节相同（6662144）；FdtBlob/ 只有 beryllium+polaris。
- **运行时无任何 dtb 覆盖机制**；换 dtb 只能构建时重编 edk2-msm，且只改 model/板级节点，**修不了 WiFi 供电卡点**。→ 彻底放弃"EFI 尾部拼 dtb"思路（已验证不生效）。

### 2.4 skip-quirk 必须保留（组织者 C4，铁证）
- Renegade 额外加的 `qcom,snoc-host-cap-skip-quirk` 正是本机 DT 自带；上游 2026-03 正在以 beryllium 名义合入同款；Kali #9767：polaris 缺它报 "msa info req rejected: 90"。**保留，不动**。

### 2.5 固件布局与配置（组织者 C7/P3）
- `ath10k/WCN3990/hw1.0/{board-2.bin, firmware-5.bin, wlanmdsp.mbn}` + `qcom/sdm845/wlanmdsp.mbn` 软链；Debian firmware-atheros 包即含。
- equuleus/polaris 未设 calibration-variant → 用默认串，**不要**照抄 beryllium 的 `xiaomi_beryllium`。
- modem 固件路径保持 polaris（已 running），勿改。

## 3. 卡点假设矩阵（更新版，按证据强度排序）

| # | 假设 | 证据 | 判定 |
|---|---|---|---|
| A | **上电时序：1.8V XO（ldo7）必须最先，且需毫秒级延时** | 官方 pwrseq 动机原文（VDD_IO first）；新芯片 pwrseq desc（vddio 第一 + pwup_delay 50-60ms）；**本机现状 = bulk 同时开、数组顺序 cx(0.8V) 先于 xo(1.8V)、零延时** | **头号候选**。低风险高信息量，先做 |
| B | **WCN3990 硬件 enable/swctrl GPIO 未被拉高**（本机 DT 无该引脚、UEFI 不拉；db845c 用 pm8998_gpios 3） | 组织者 P2 ⚠ 标注引脚未验证；beryllium 主线可跑（但靠 ABL） | 次候选。若 A 无效，查小米主板对应 GPIO（需原理图/实测扫描） |
| C | rf_clk2 时钟实际未输出（refcount≠物理输出） | enable_count=1 仅内核侧计数 | 低（vdd 后 clk 顺序正确，rpmh 一般正常）；A/B 无效后验证 |
| D | WCN3990 ROM 启动需要 > 数百 ms，查询时点太早 | 无直接证据 | 已排除（开机后多次查询） |
| E | QRTR/IPCRTR 时序或命名服务问题 | 机制已源码级确认完好（LOOKUP 本地、REGISTER 走 IPCRTR） | 已排除 |

**已排除清单**（组织者 18 + 本地核验）：DT 缺 IPCRTR（假）、CONFIG_QRTR_NS（无此符号）、固件缺失（已补）、msa 1M（db845c 同规格）、upstream mba（原厂替代）、UEFI/DT 错误（polaris DT 自带 quirk+5 路）、pwrseq 路线（6.19 未接入）、换 dtb（修不了供电且运行时无机制）。

## 4. 下一步行动（单一变量，不盲目试错）

**P0（手机开机后，10 分钟，只观测不改）**——组织者原话 + 本机适配：
1. `dmesg | grep -i 'soc power on'`——**关键判据**：
   - **出现** "soc power on" → hif_power_up 被跑到 → 说明 FW_READY 事件曾到达（wlanfw 注册过）→ 卡点在 host_cap/msa/固件上传段 → 查 dmesg 是否有 "msa info req rejected"/ath10k err
   - **不出现** → core_start 从未触发 → wlanfw 从未注册 → 卡点在 server arrive 之前 → 走动作 A
2. `dmesg | grep -iE 'ath10k|qmi|qrtr|wcn|fw'` 尾部 30 行，确认有无任何 ath10k 报错
3. `cat /sys/kernel/debug/regulator/*/state`（若有 debugfs）复核 5 路 LDO 电压与状态

**动作 A（头号，时序修正）**：改 snoc.c 1783 处，拆 bulk 为顺序 enable：
```
regulator_enable(vregs[1]);          // vdd-1.8-xo（XO 1.8V，应最先）
usleep_range(50000, 100000);         // 50-100ms（对齐官方 pwup_delay 50ms 量级）
regulator_enable(vregs[0]);          // vdd-0.8-cx-mx
regulator_enable(vregs[2]);          // vdd-1.3-rfa
regulator_enable(vregs[3]);          // vdd-3.3-ch0
regulator_enable(vregs[4]);          // vdd-3.3-ch1
usleep_range(50000, 100000);
```
clk enable 保持现状（vdd 之后）。失败路径逆序 disable。重编→拼 EFI→写 ESP→重启→P0 观测。
- 结果判定：wlanfw 注册 → 根因坐实（时序）→ 继续 wlan0/连接；不注册 → 转动作 B（GPIO 排查），**不再重复 A**。

**动作 B（若 A 无效）**：排查 WCN3990 enable/swctrl GPIO——对照 db845c（pm8998_gpios 3）与小米主板原理图；可在内核命令行/设备树 overlay 里探测 gpiochip 各 pin 拉高后观察 wlanfw 是否注册（此步需谨慎，逐 pin 实验并记录）。
