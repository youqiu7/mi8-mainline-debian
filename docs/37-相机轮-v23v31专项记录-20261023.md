## 2. 三个决定性陷阱（按坑力排序）

1. **Qcom CCI 驱动的位置与 config 名**：`drivers/i2c/busses/i2c-qcom-cci.c`、`CONFIG_I2C_QCOM_CCI`——**不在 camss 目录**！主线/社区 sdm845 树都没有 camss/cci.c（曾误以为有）。`find -name "cci*"` 会漏掉 i2c-qcom-cci.c。**web 搜索 5 分钟定案**（用户新规则首次生效：BT 之后相机轮又一次验证）。
2. **Kconfig tristate 依赖链**（第三次踩）：`MEDIA_SUPPORT=m → VIDEO_DEV=m → VIDEO_QCOM_CAMSS 上限 m`。一次 olddefconfig 不会连带把依赖链源头拉成 y，必须 `MEDIA_SUPPORT=y + MEDIA_CAMERA_SUPPORT=y` 显式开。
3. **gpio-regulator 的 states 格式**：`states = <v0>, <v1>` 缺状态数会 -22；`states = <2>, <v0>, <v1>` 仍 -12（驱动解析路径有坑，未深究）。**绕法（v30 采用）**：supply 用 regulator-fixed always-on + **tlmm pinctrl `output-high` 直接在启动时拉高使能脚**（75=VIO、99=VDIG、40=AVDD 开关）——pinctrl 是"零驱动"供电开关，屡试不爽。

## 3. 硬件接线定案（本机实测+社区互证）

- **主摄=IMX363**（维基公开资料，与 MIX 2S/Pixel 3 同款；社区 joel/beryllium-imx363 实测先例）
- **reset=tlmm GPIO80**（ACTIVE_LOW，与 beryllium 同）；**MCLK0=GPIO13 24MHz**（camcc index 66=0x42；tlmm function "cam_mclk"=func18 覆盖 gpio13-16，db845c 同款写法）
- **供电**：VIO=tlmm75（micode camera_viodd_ldo 2.8V）、AVDD=tlmm40（2.864V，vendor 另经 pm8998_ldo22）、VDIG=tlmm99（1.35V）——**micode equuleus-p0-camera-sensor-mtp.dtsi 36-104 行**是唯一权威接线表
- **CCI 地址**：i2c-16（master0）；**EEPROM@0x50、0x54 已应答**（总线硬件确认通）
- camss 地址核对：实机节点名 a00000 但 reg=0x0acb3000（与主线一致，节点名仅 vendor 习惯）

## 4. 剩余卡点（下一轮从这里继续）

**imx363 0x10 NACK（-6）**，三候选按嫌疑排序：
1. **MCLK pin mux 未实际生效**：pinmux-pins 显示 pin13 UNCLAIMED（但注意：40/75/99 的 output-high 也没在 pinmux-pins 显示 claim，此 debugfs 显示机制存疑——不能仅凭 UNCLAIMED 定罪）。**验证法**：`media-ctl -d ... --set-v4l2 /entity/...` 流配置时看 clk；或读 camcc MCLK0 的 enable_count 在 probe 瞬间（ftrace）；或硬件示波。
2. **sensor 真实地址≠0x10**：i2cdetect 全扫 0x03-0x77 只见 0x50/54。Sony IMX363 常见 0x1A/0x36/0x10——若 MCLK 正常仍全空，则 sensor 未上电/未复位释放。
3. **供电时序/电压**：pinctrl output-high 是"常开"（早期上电）——无时序问题；但 VIO=2.8V 与 IMX363 典型 1.8V VIF 存疑（micode 标 2.8V，硬件 rail 由板级 DCDC 决定，标签不影响物理——若硬件本就 2.8V 设计则无碍）。

## 5. 驱动代码要点（imx363.c 1513 行，GPL-2.0，Intel/Joel）

- probe 顺序：regmap(16bit) → regulators → clk(clock-frequency 属性 24M) → endpoint(lanes/link-freq) → **reset GPIOD_OUT_LOW** → **imx363_power_on(regulators→400us→reset逻辑0→clk_enable→1ms)** → **identify(读 0x0016)** → controls → 注册 subdev
- power_off 与 power_on 互逆（runtime PM）；失败路径回滚（所以 clk_summary/gpios 看到的是失败后状态）
- **reset 语义与 ACTIVE_LOW 配套**：驱动逻辑 1=复位、0=释放（beryllium ACTIVE_LOW 下物理低=复位、物理高=释放）

### 把握度评估（2026-10-23 13:10）

- **软件配置正确**：~85%（与 beryllium/db845c 社区实证 1:1 同款；窗口实测三件套全绿；无法证伪的只剩 MCLK pin mux 的物理输出）
- **MCLK pin13 实际输出 24MHz**：完全未知（clk framework 已 enable 但 pin mux 物理输出需示波器/万用表；debugfs 的 pinmux-pins UNCLAIMED 显示不可靠）
- **IMX363 芯片/排线健康**：~40%——三地址（0x10/0x1a/0x0e）全不应答（连 ACK 无），而同模组 EEPROM/0x0e 芯片供电即活——**指向 IMX363 特有失效**（XVCLK 无输入/芯片供电域/芯片本体/排线接触）。**用户拆机换屏下指纹套件时动过内部，排线因素概率不低**
- **供电电压域疑点**：米8 viodd 标 2.8V（beryllium vif=1.8V）——若 XVCLK pin 的 IO 域真是 2.8V，1.8V 器件的 IMX363 XVCLK 输入超压（硬件设计层，软件不可改）

### 事故教训（本轮）

- **devmem 读 tlmm io 区（0x3400000）→ 内核硬挂**（IO_STRICT_DEVMEM 路径），用户手动 fastboot 重启。**红线：设备上禁用 /dev/mem 直读寄存器**
- 窗口实验的正确姿势：**unbind→bind→0.6s 后读 regulator/gpio/clk**（开机自动 probe 的 8s 窗口会错过 SSH 回线）
- sysfs gpio 不可用（CONFIG_GPIO_SYSFS 未开）；regulator sysfs 的 state 是窗口观察的可靠通道

### 双战线证据链（终审）

| 设备 | 需 XVCLK | i2c 应答 |
|---|---|---|
| EEPROM 0x50/54 | 否 | ✅ |
| actuator 0x0e | 否 | ✅ |
| IMX363 主摄 | 是 | ❌（fs 全扫/PLL 手动开/供电全绿后仍否） |
| OV9282 IR | 是 | ❌（同上） |

**软件层已证**：时钟树（PLL2 480M→src 24M 手动 prepare 成功）、mux fs 全 8 值、供电（regulator enabled/gpio high/PD 应用）、地址、时序、社区+vendor 全参数。**软件无法证明的物理项仅剩两个**：①XVCLK 是否真出 pin13/14（mux fs 表值与 vendor 一致但物理输出未测）②AVDD/DVDD rail 物理电压（L22/tlmm27/tlmm99 软件绿）。“需要 XVCLK 的全灭、不需要的全活”模式与两者任一缺失都吻合。

### 结论

相机轮挂起（等 20-30 元 USB 逻辑分析仪终审 pin13+I2C 两线，或维修店借示波 5 分钟）。IR 轮的框架成果（v43/v44 的完整 OV9282 节点+时钟配置方法）与主摄共用，终审后两摄可同轮点亮。**ESP 现行=v46**（含全部 camera 节点+PLL 打印+FSSCAN，不影响其他子系统，开机拖慢 ~15s 可接受）。
