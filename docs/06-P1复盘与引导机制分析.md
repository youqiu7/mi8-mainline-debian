# P1 失败复盘 + 引导机制分析（严谨版）

日期：2026-10-20 · 结论：**放弃 ABL + appended DTB 路线，转走 UEFI (EDK2)**

---

## 1. 权威资料怎么说（不是我猜的）

### 1.1 ABL 期望的 boot 镜像格式

U-Boot 官方文档 `doc/board/qualcomm/sdm845.rst`（把 U-Boot 塞进 Android boot 镜像、由 ABL 引导的官方做法）原文：

> We'll assemble android boot image with `u-boot.bin` instead of linux kernel,
> and FIT image instead of `initramfs`. **Android bootloader expect gzipped kernel
> with appended dtb, so let's mimic linux to satisfy stock bootloader.**

它给出的"合法 payload"构造方式：

```bash
# mock dtb —— 注意：只有 memory + chosen，没有 board-id、没有 compatible
dtc -I dts -O dtb -o payload_mock.dtb << EOF
/dts-v1/;
/ {
    #address-cells = <2>;
    #size-cells = <2>;
    memory@80000000 {
        device_type = "memory";
        /* We expect the bootloader to fill in the size */
        reg = <0 0x80000000 0 0>;
    };
    chosen { };
};
EOF

gzip u-boot.bin
cat u-boot.bin.gz payload_mock.dtb > u-boot.bin.gz-dtb     # ← kernel 段 = gzip + 追加 dtb

mkbootimg --base 0x0 --kernel_offset 0x00008000 \
  --ramdisk_offset 0x02000000 --tags_offset 0x01e00000 \
  --pagesize 4096 --second_offset 0x00f00000 \
  --ramdisk "$fit_image" --kernel u-boot.bin.gz-dtb -o boot.img
```

**两个关键事实**：
1. ABL 要求 **gzipped kernel + 追加 dtb**（我们的 v1 符合）；
2. ABL 会**自己往 memory 节点里填 size**（所以 mock dtb 写 `reg = <0 0x80000000 0 0>`）。

### 1.2 Linaro 关于 dtbo 的警告

> Many of the most recent boards ship with a dtbo partition and when loading a kernel
> and DTB, **the bootloader will overlay the DTB with the content of the dtbo partition
> causing it to go badly**. In order to avoid this situation, it is recommended to
> erase/program the dtbo partition.

我们的 `dtbo` 分区已经是全 0（Mindows 时代被擦），这一条**已经满足**。

### 1.3 原厂 boot.img 的真实结构（我拆出来的）

```
boot.img (64 MiB, header v1, page 4096)
└─ kernel 段 44,499,364 B
   ├─ gzip 部分 14,144,245 B  →  解压得 Image 42,176,520 B (40.2 MiB)，magic "ARMd" ✓
   └─ 偏移 14,144,245 起：FDT magic d00dfeed，dtb 长 494,265 B
      model = "Xiaomi Technologies, Inc. **Dipper** new MP v2.1"
```

**注意两件事**：
- 原厂 kernel 段**确实是 "gzip + 追加 dtb"**，与 U-Boot 文档完全一致；
- **但里面装的是 dipper 的 DTB，而设备运行时的 `/proc/device-tree/model` 是 "Equuleus MP v2.1"**。
  → 说明 MIUI 的 boot.img 是三机型通用件，ABL 最终交给 Android 内核的并不是这份 dtb。

## 2. 我们做过什么，结果如何

| 版本 | 格式 | cmdline | 结果 |
|---|---|---|---|
| v1 | header v1 + `Image.gz` 追加 dtb（**与原厂结构一致**） | 含 `earlycon=qcom_geni` | 黑屏 → 40~50 s 后小米 logo → 关机 |
| v2 | header v2 + 独立 dtb 段（`dtb_size`/`dtb_addr`） | 同上 | 黑屏、无 USB、无 COM |

**对照实验（关键）**：`fastboot boot` **原厂 boot.img → 30 秒内正常启动 Android**。
→ 结论：`fastboot boot` 通道完全正常，问题在我们镜像的内容/兼容性，不是通道。

## 3. 为什么"看起来内核在跑"却什么都看不到

- 设备完全没有 USB 枚举（连 dwc3 都没 probe），说明内核要么没起来，要么起来后立刻死了；
- 没有 UART（决策 D3：不拆机），没有 pstore（我们的 DTB 里没 ramoops 节点，而且如果 ABL 不用我们的 DTB 就更没有）；
- **屏幕是唯一可能的输出，而它依赖 simplefb —— simplefb 又依赖"我们的 DTB 被采用"**。
  这就形成死锁：**要看到输出，必须先让 DTB 生效；要验证 DTB 是否生效，又必须先看到输出。**

### 前人也没走通这条路

**`screen = N` 正是同一个死结**。也就是说，"ABL + 主线内核 + 自己 DTB"这条路，**在这台设备上从没被走通过**。

**UEFI 路线为什么能解开死锁**：

1. **UEFI 自带屏幕驱动**（`SimpleFbDxe`，来自 Lumia950XLPkg）→ **一开机就有画面**，观测通道立刻可用；
2. Linux 内核和 **DTB 由 UEFI 从 ESP 分区读取**，我们想换就换，**不再受 ABL 的 appended-dtb 机制约束**；
3. UEFI 有 Shell，可以 `load`/`map`/看设备、读分区 —— 调试能力比现在强一个量级；
4. 用户这台机器**本来就装过 Mindows（同一套 EDK2 方案）**，`mindowsesp`(300 MB) / `mindowswin`(59.7 GB) 分区都还在，等于环境已经铺好过一次。

## 5. 下一步（严格按"先验证再落地"的顺序）

**第 0 步（零风险）**：`fastboot boot boot-dipper.img`
- 不写任何分区，失败就重启回 Android
- 成功判据：**屏幕上出现 EDK2/UEFI 的界面**（哪怕只是几行字）
- 这一步就能确认：UEFI 固件在这台 equuleus 上能不能跑、屏幕能不能亮

**第 1 步**：如果 UEFI 起来 → 进 UEFI Shell，看它认不认 UFS 分区、能不能读到 `mindowsesp`
- 这一步确认存储与文件系统

**第 2 步**：把 Linux（内核 + 我们的 equuleus DTB + initramfs）放到 ESP，从 UEFI 启动
- DTB 用我们已有的 `sdm845-xiaomi-equuleus.dtb`，此时**它一定会被使用**（UEFI 直接读文件）
- 屏幕这里会从"UEFI 界面"过渡到"内核 fbcon 日志"——第一次能看到内核在做什么

**第 3 步**：确认可用后才谈 rootfs 落地（`sda23`）与双系统引导项

## 6. 风险与回滚

| 风险 | 说明 | 回滚 |
|---|---|---|
| `fastboot boot` 失败 | 不落盘 | 长按电源重启 |
| UEFI 固件针对 dipper 而非 equuleus | 屏幕/触摸参数可能不同；可能显示异常甚至不显示 | 仍然只是 boot once，不落盘 |
| 后续若要固化 UEFI | 需写入 `boot` 分区（原厂已备份 `c7da48be…`） | `fastboot flash boot 备份.img` |
| 数据 | 本阶段**不动任何分区** | — |

## 7. 教训（写进技能库）

1. **先查权威文档再动手**：U-Boot 的 sdm845 文档一句话就说明了 ABL 要什么格式，我却在打包参数上试了三轮。
2. **先找现成移植**：`edk2-porting/edk2-msm` 直接有 `boot-dipper.img`，pmOS wiki 也早就写明 `screen = N` —— 说明这条路前人试过且没通。
3. **没有观测通道就不要动手**：在"屏幕黑 + 无 UART + 无 pstore"的状态下刷机，等于闭眼改代码。
4. **一个能点亮屏幕的引导器（UEFI）比一百次猜测有用**。
